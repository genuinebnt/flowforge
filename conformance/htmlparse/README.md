# htmlparse conformance data

Language-neutral data and procedures for the Go `htmlparse` package and its
Rust port. Both implementations must produce the same results on the same
suites.

## Files

* `entities.json` — the WHATWG named character references (2231 entries)
  in the standard's `entities.json` format: `{"&name": {"codepoints":
  [...], "characters": "..."}}`, keys sorted bytewise, names with and
  without `;` as separate entries. Generated by `htmlparse/internal/gen`
  (`go generate ./htmlparse`) together with `htmlparse/entities_table.go`;
  identical to html5ever's `web_atoms` table. The Rust port generates its
  table (sorted names + prefix trie) from this file.
* The suites themselves are vendored unmodified in
  `conformance/third_party/` (see its README for commits and licences):
  `html5lib-tests/tokenizer/*.test` and `wpt-html-parsing/*.dat`.

## Tokenizer suite (html5lib JSON)

For each test and each entry of `initialStates` (default `Data state`):

1. Decode `input` keeping lone surrogate escapes (`\uD800`) as WTF-8 bytes
   (`encoding/json` / `serde_json` replace them; use a raw decoder). With
   `doubleEscaped`, unescape `\uXXXX` once more in the input and in every
   expected string.
2. Tokenize with the initial state, `lastStartTag`, and CDATA disallowed
   (there is no tree).
3. Map lone surrogates in expected strings to U+FFFD (our output policy),
   coalesce adjacent `Character` tokens on both sides, and compare tokens
   (`["DOCTYPE", name|null, public|null, system|null, !forceQuirks]`,
   `["StartTag", name, {attrs}, true?]`, `["EndTag", name]`,
   `["Comment", data]`, `["Character", data]`,
   `["ProcessingInstruction", target, data]`).
4. Compare `errors` in order: code, line and column (1-based; columns in
   UTF-16 code units; CR LF counts as one line break). For
   `xmlViolation.test` apply the infoset coercion (FF → space,
   noncharacters → U+FFFD, `--` → `- -` in comments) and skip errors.

Expected result: tokens 7050/7050; 16 error-position mismatches, exactly
`test3.test#1167`–`#1182` (`<?x x` EOF cases; see
htmlparse/OPEN_QUESTIONS.md Q-TOK-1).

## Tree-construction suite (.dat)

Sections are lines that are exactly `#data`, `#errors`, `#new-errors`,
`#document-fragment`, `#script-off`, `#script-on`, `#document`,
`#description`. `#data` runs to the next section (final newline removed);
`#document` runs to the next `#data` minus trailing empty lines. A test id
is `<file>#<0-based index>`.

* Scripting flag: on for `#script-on`, otherwise off.
* `#document-fragment` `td` / `svg path` / `math mi`: run fragment parsing
  with that context element (HTML namespace unless prefixed).
* Compare the html5lib dump exactly: `| ` + two spaces per depth;
  `<!DOCTYPE name>` or `<!DOCTYPE name "public" "system">` when either id
  is non-empty; `<name>`, `<svg name>`, `<math name>`; attributes on the
  following lines sorted by displayed name (`xlink href`, `xml lang`,
  `xmlns xlink`); `"text"`; `<!-- data -->`; `<?target data?>`; template
  contents under a `content` line.
* `#errors` are not compared.

Expected result: 1967/1973; the failures are exactly the six
`scripted_*.dat` cases (script execution).

## Invariants

The port reimplements HTML-INV-01 … HTML-INV-11 (htmlparse/README.md,
"Invariants (port these)") with the same generators: seeded tag soup and
well-formed documents drawn from SplitMix64 (`core.SplitMix64`), plus every
`.dat` input. HTML-INV-04 compares allocations per byte at n and 4n bytes
(repeated units, bound 1.2) and time per byte (bound 1.5).
