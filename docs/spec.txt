# Flowforge Specification

A language-agnostic design for Flowforge, a durable workflow engine with a typed DSL, a bytecode VM and agent steps, and Sentinel, the scope-enforced asset graph it feeds. The graph model follows the OWASP Amass Open Asset Model (OAM).

Version 0.1 (draft)Date 2026-11-12Audience: implementers in any language (reference targets: Go, then Rust)

## 1. About this document

### 1.1 How to use it for code generation

- Section 11 protobuf contracts, then generate client and server stubs.

- Sections 7 and 8 DSL front end, then bytecode and VM.

### 1.2 Conventions

 | Topic | Rule

 | Normative words | MUST, MUST NOT, SHOULD and MAY are used in their RFC 2119 sense.

 | Identifiers | UUIDv7 in canonical lowercase text form, generated by the service that owns the row. Public IDs carry a prefix in REST: run_, prg_, ent_, apr_, usr_, ten_, wf_.

 | Time | RFC 3339 in UTC with millisecond precision in JSON (2026-11-12T13:25:11.042Z). Postgres timestamptz. Durations in JSON are integer milliseconds with an _ms suffix.

 | JSON | snake_case keys, no unknown-field tolerance on requests (reject), full tolerance on responses (ignore).

 | Enums | Lower snake case strings in JSON and SQL; upper snake case in protobuf with an _UNSPECIFIED = 0 value.

 | Tenancy | Every row, message and cache key carries tenant_id. A handler that reads data without filtering by tenant is a defect.

 | Money | Integer minor units plus ISO 4217 currency code. Never floats.

 | Errors | See sections 11.7 (gRPC) and 12.2 (REST). Error reason codes are stable identifiers.

## 2. System overview

### 2.1 Purpose

Flowforge runs workflows written in a typed DSL. A workflow orchestrates tools (recon tools, ERP actions, LLM calls) as durable, replayable effects. Sentinel stores what the tools learn as a graph of assets and relations. A program's scope bounds everything: no tool may touch a target that scope does not allow.

### 2.2 Glossary

 | Term | Meaning

 | Tenant | An account boundary. All data and quotas are per tenant.

 | Program | A bounded engagement (for example a bug bounty program) with a versioned scope and rules of engagement.

 | Scope | Versioned allow and deny rules plus the maximum activity class, rate limits and time windows for a program.

 | Workflow | A named, versioned DSL program that is type-checked, compiled to bytecode and stored.

 | Run | One execution of a workflow version against a scope version, recorded as an append-only event log.

 | Effect | An interaction with the outside world requested by the VM (tool call, approval wait, sleep, LLM call, scope check). Effects suspend the VM.

 | Tool | A registered adapter with a typed signature, an effect class and a rate limit.

 | Observation | A normalized batch of entities, edges and tags emitted by one tool invocation.

 | Entity / Edge / Tag | Graph node, directed relation and attached property, as in the Open Asset Model.

 | Plan | DSL source proposed by an agent step. It is checked exactly like human-written code before it can run.

 | Activity class | passive (public data sources), active (direct traffic to targets), intrusive (testing that can affect availability or data).

### 2.3 Goals and non-goals

GoalsDurable runs that survive crashes and replay deterministically. A typed DSL where scope and effects are visible to the compiler. A graph compatible with OAM. Per-tenant isolation. Human approval for risky actions. Full audit of every decision.

Non-goals (v0.1)General-purpose programming. Running untrusted native code. Exploit execution. Multi-region active-active. A hosted marketplace of tools.

### 2.4 Invariants

These MUST hold in every implementation.

- Scope: no active or intrusive tool call executes unless the scope service allowed that exact normalized target under the run's scope version, and the decision is in the event log.

- Determinism: given the same bytecode and the same recorded effect results, the VM reaches the same state. The VM has no clock, randomness or I/O of its own.

- Append-only log: run events are never updated or deleted during a run's life. State is derived from them.

- Agents propose, the engine disposes: an agent can only emit DSL source. Type, effect, scope and policy checks run outside the model.

- Tenant isolation: no query, cache key or event crosses a tenant boundary.

- No silent success: an unreachable scope service, rate limiter or policy engine means deny, not allow.

## 3. Architecture

### 3.1 Services

 | Service | Owns | Sync API | Async

 | gateway | Users, tenants, sessions, API keys (identity module) | REST /v1 (public), gRPC client to all | Publishes auth.events

 | engine | Workflows, runs, run events, effects, approvals, timers | EngineService | Publishes run.events, approval.events

 | tool-runner | Tool registry (code), sandboxes, per-tool rate state | ToolRunnerService | None

 | scope | Programs, scope versions, decision log | ScopeService | Publishes scope.events

 | graph | Entities, edges, tags, observations, change events, search index | GraphService | Publishes graph.changes (outbox)

 | similarity | Embeddings index (pgvector, then DiskANN segments), tombstones, hybrid search | Similarity (section 22.9) | Subscribes to graph.changes

 | notifier | Alert rules, deliveries, dedupe state | NotifierService (admin) | Subscribes to all event topics

### 3.2 Communication rules

- gRPC (HTTP/2, TLS) for request/response and streaming between services. Every call carries metadata authorization (internal token), x-tenant-id, x-request-id, traceparent, and an optional idempotency-key. Every call sets a deadline.

- Pub/Sub for fan-out events. Producers write events to an outbox table in the same transaction as the state change; a relay publishes them at-least-once. Consumers MUST be idempotent, keyed by event_id.

- Only gateway is reachable from the internet. Internal services trust the gateway's internal token, never a client-supplied identity.

- tool-runner has no direct internet access. Its only route out is the scope-checked egress proxy.

### 3.3 Life of a run

- Client calls POST /v1/runs with a workflow version, inputs and Idempotency-Key. The gateway authenticates, authorizes, and forwards SubmitRun.

- Engine pins the current scope version, loads bytecode, records run_submitted, and schedules the run.

- A scheduler worker leases the run, loads recorded events, and drives the VM until it suspends on an effect.

- For a tool effect the engine calls scope.Check, records scope_decision, then ToolRunner.Execute. The runner re-checks scope per target and streams observations.

- Engine records effect_completed and forwards observations to graph.IngestObservations. Graph writes entities and edges, computes changes, and emits graph.changes.

- Notifier evaluates alert rules on those changes. Agent and approval effects follow the same record-then-act pattern.

- When the VM returns, the engine records run_succeeded or run_failed, and the final state is derived from the log.

## 4. Scope model

### 4.1 Program scope document

{
  "program_id": "prg_01JD8K2XH3",
  "version": 7,
  "name": "Acme public bug bounty",
  "effective_from": "2026-11-01T00:00:00.000Z",
  "rules": [
    { "id": "r1", "effect": "allow", "kind": "domain",          "value": "acme.com",          "note": "apex only" },
    { "id": "r2", "effect": "allow", "kind": "wildcard_domain", "value": "*.acme.com",        "note": "all subdomains, any depth" },
    { "id": "r3", "effect": "allow", "kind": "cidr",            "value": "203.0.113.0/24" },
    { "id": "r4", "effect": "deny",  "kind": "domain",          "value": "payments.acme.com", "note": "explicitly excluded" },
    { "id": "r5", "effect": "deny",  "kind": "wildcard_domain", "value": "*.corp.acme.com" },
    { "id": "r6", "effect": "allow", "kind": "url_prefix",      "value": "https://api.acme.com/v2/" }
  ],
  "activity": {
    "max_class": "active",
    "prohibited": ["dos", "social_engineering", "credential_stuffing"],
    "rate": { "requests_per_second": 5, "burst": 10, "concurrency": 4 },
    "windows": [ { "days": ["mon","tue","wed","thu","fri"], "start": "09:00", "end": "18:00", "tz": "UTC" } ]
  }
}

 | Field | Rules

 | rules[].kind | domain (exact name), wildcard_domain (*. prefix; matches any depth below the name, never the apex itself), cidr (IPv4 or IPv6 prefix), url_prefix (scheme, host, port and path prefix on a segment boundary), asn (value AS64500, allowed only as informational input to discovery, never as sole permission for active work).

 | rules[].effect | allow or deny. Deny always wins over allow. No match means deny.

 | activity.max_class | Highest activity class any run of this program may perform. A workflow whose inferred effect exceeds this fails the compile-time policy check and is also refused at run time.

 | activity.rate | Program-level ceiling, enforced by the limiter (section 14) in addition to tenant and tool limits.

 | activity.windows | Allowed testing windows. Outside a window only passive effects may run; active ones wait.

 | version | Monotonic integer. A run is pinned to one version. Publishing a new version pauses in-flight runs of that program at their next effect boundary and re-validates them.

### 4.2 Normalization (MUST run before any match)

- Domain names: trim, lowercase, remove one trailing dot, convert to IDNA A-label (punycode), reject empty labels, reject names longer than 253 octets or labels longer than 63.

- URLs: parse; lowercase scheme and host; strip default ports (:80, :443); drop fragment; reject userinfo (credentials in URL) for scope decisions; percent-decode unreserved characters; collapse . and .. path segments.

- IP addresses: parse strictly (no octal, hex or decimal-integer IPv4 forms); output canonical text; map IPv4-mapped IPv6 to IPv4.

- Anything that fails to normalize yields decision deny with reason invalid_target.

### 4.3 Decision algorithm

function check(target, class, scope, now) -> Decision
  t = normalize(target)                       // section 4.2
  if t is invalid:                            return deny("invalid_target")
  if class > scope.activity.max_class:        return deny("class_exceeds_program")
  if class != passive and not in_window(now): return deny("outside_window")
  for rule in scope.rules where rule.effect == deny:
      if matches(rule, t): return deny("explicit_deny", rule.id)
  if class != passive and t is hostname:
      ips = resolve_once(t)                   // pinned for the connection that follows
      for ip in ips:
          for rule in scope.rules where rule.effect == deny and rule.kind == cidr:
              if matches(rule, ip): return deny("resolved_ip_denied", rule.id)
  for rule in scope.rules where rule.effect == allow:
      if matches(rule, t): return allow(rule.id, pinned_ips=ips)
  return deny("no_matching_allow")

A decision is { decision, reason, rule_id, scope_version, target, pinned_ips[], decided_at }. The same object is stored in the scope_decisions table and the run's event log.

### 4.4 Enforcement layers

 | Layer | Mechanism | Failure mode

 | Compile time | Active tools accept only InScope<T> parameters. The only constructor is scope.check(x). | Program does not compile (error E0301).

 | Engine | Calls scope.Check before scheduling a tool effect and records the decision. | Deny: effect fails with scope_denied.

 | Tool-runner | Re-checks per concrete target before starting a process (tools may expand one input into many targets). | Deny: target skipped and logged.

 | Egress proxy | Every outbound connection is checked against the pinned decision: host, resolved IP, redirects. | Connection refused and logged.

 | Graph ingest | Every entity gets scope_status (in_scope, out_of_scope, unknown). Only in_scope entities may become inputs to active steps. | Entity stored for context but never targeted.

 | Agent | Plans are compiled and checked like any source. | Plan rejected, counted as a metric.

 | Kill switch | Per program and global flag checked by the engine and the proxy. | Runs cancelled, new calls blocked.

### 4.5 Edge cases the implementation MUST handle

- Redirects and CNAME chains: re-run check on every hop. A redirect to an out-of-scope host is not followed.

- Check-then-use race: connect only to pinned_ips from the allow decision. Never re-resolve between check and connect.

- Shared hosting and CDNs: permission attaches to the hostname rule, never to an IP alone.

- URL tricks: https://acme.com@evil.com/, https://acme.com.evil.com/, mixed case, trailing dot, punycode lookalikes, IPv6 zones, decimal IPs. All covered by normalization plus host-only matching.

- Scope changes mid-run: see version semantics above.

## 5. Graph model (Open Asset Model aligned)

### 5.1 Principles

- The graph stores entities (nodes holding one OAM asset), edges (typed, directed relations between entities) and tags (properties attached to an entity or an edge). This mirrors the OAM and its asset-db library, where each of these also carries created_at and last_seen.

- Asset and relation type names, labels and field names use OAM names so that data can be exported to or imported from Amass-compatible tooling.

- Flowforge adds tenant, program, scope status, confidence, provenance and lifecycle columns around the OAM content (tagged ff). They never change the meaning of the OAM content.

- OAM assets are JSON documents. The graph keeps them as a jsonb column plus a canonical key used for de-duplication.

### 5.2 Taxonomy

 | Category | Asset types

 | Network infrastructure | FQDN, IPAddress, Netblock, AutonomousSystem

 | Registration | DomainRecord, IPNetRecord, AutnumRecord

 | Digital artifacts | URL, Service, TLSCertificate, File

 | Organization and people | Organization, Person, Location, Phone, ContactRecord

 | Identity | Identifier

 | Financial | Account, FundsTransfer

 | Product | Product, ProductRelease

The OAM docs list these 21 types and describe the list as open-ended. Flowforge v0.1 implements the network, registration, digital-artifact and product groups, and stores unrecognized or later types opaquely (type name plus JSON content) so imports do not fail.

### 5.4 Asset types

The canonical key is the Flowforge de-duplication key (ff), unique per (tenant, program, type, key). OAM docs did not specify a dedup key for most types, so these are Flowforge decisions. Status tags show how I sourced each field list.

 | Asset | Content fields | Canonical key | Source

### 5.7 Ingest and merge semantics

- Resolve: for each entity in an observation compute key. Upsert by (tenant, program, asset type, key). If new, set created_at = last_seen = observed_at. If existing, set last_seen = max(last_seen, observed_at) and merge content with non-empty wins, newest wins on conflict.

- Edges: upsert by (from_entity, to_entity, relation type, label, relation discriminator), where the discriminator is port_number+protocol for port relations and rr_type for DNS relations.

- Provenance: add one SourceProperty per (tool, entity or edge). Confidence from several independent sources combines as 1 - Π(1 - cᵢ), where each cᵢ is the highest confidence reported by one source, and is capped at 0.99.

- Scope status: computed by calling the same matcher as section 4 in passive mode (no resolution). Unknown is never promoted to in-scope by inference.

- Staleness: an entity becomes stale when the sources that previously reported it completed a covering run (same tool, same input) and did not report it for stale_after_runs (default 3) consecutive runs. It becomes active again when seen. Nothing is hard-deleted; deletion is an explicit admin action recorded in the audit log.

- Change events are produced in the same transaction through the outbox, one per effective change: entity_added, entity_changed (with a JSON patch), entity_stale, entity_reactivated, edge_added, edge_removed (stale), scope_status_changed.

### 5.9 Traversal and analysis operations

 | Operation | Semantics

 | neighbors(entity, labels?, direction, depth, since?) | Breadth-first, bounded depth (max 6). Returns entities and edges, each at most once. since filters on last_seen.

 | path(from, to, max_cost) | Dijkstra over edges with cost -ln(confidence), minimizing total cost. Returns the path and its combined confidence.

 | blast_radius(entity, depth) | Entities reachable through ownership and hosting labels (dns_record, port, certificate, contains, owns), ranked by distance.

 | diff(run_a, run_b) or diff(since) | Set difference of entity and edge keys between two points; changed content reported as JSON patches. Implemented from change events, not by scanning.

 | components() | Connected components via union-find, used to group assets into services or organizations.

 | search(query, types?, limit) | Trigram index over entity display text (names, addresses, URLs, banners). Substring and typo tolerant; results verified by exact substring check, then ranked by trigram similarity.

## 6. Observations and tool adapters

### 6.1 Observation envelope

Tools never write to the graph. They return observations, and the engine forwards them to GraphService.IngestObservations.

{
  "observation_id": "obs_01JD8K3M2Q",
  "tenant_id": "ten_01JD...", "program_id": "prg_01JD8K2XH3", "run_id": "run_7f3a91",
  "step": "probe", "effect_seq": 14,
  "tool": { "name": "httpx", "version": "1.6.9" },
  "observed_at": "2026-11-12T14:02:12.311Z",
  "confidence": 0.9,
  "entities": [ { "ref": "u1", "asset": { "type": "URL", "url": "https://api.acme.com/", "scheme": "https", "host": "api.acme.com", "port": 443 } } ],
  "edges":    [ { "from": "u1", "to": "ent_01JD8K3A7Q", "relation": { "type": "SimpleRelation", "label": "domain" } } ],
  "tags":     [ { "target": "u1", "property": { "type": "SimpleProperty", "name": "title", "value": "Acme API" } } ],
  "raw_ref": "gs://flowforge-artifacts-prod/ten_01JD.../obs_01JD8K3M2Q.json.zst"
}

- ref values are local to the envelope. An edge endpoint is either a local ref or an existing entity id.

- Raw tool output is stored in object storage and referenced by raw_ref. It is never fed to an agent directly (section 16).

- An envelope MUST be idempotent: ingesting the same observation_id twice has no additional effect.

### 6.2 Tool specification

{
  "name": "httpx",
  "version": "1.6.9",
  "description": "HTTP probing and fingerprinting",

### 6.3 Adapter contract

- An adapter implements: spec() → ToolSpec, and run(input, ctx) → stream of Observation.

- The adapter MUST NOT open network connections itself except through the proxy provided in ctx.

- It MUST stream results as they are produced (batches of at most 500 entities), and MUST stop within 2 seconds of a cancel signal.

- It MUST normalize values with the functions in section 4.2 before emitting entities, so keys match across tools.

- It reports progress as { items_done, items_total? } and structured errors with a retryable flag.

### 6.4 Example tool mappings

 | Tool (example) | Class | Emits

 | Subdomain enumeration (passive sources) | passive | FQDN entities; SourceProperty per source

 | DNS resolution | passive (public resolvers) or active (direct to authoritative) | IPAddress; dns_record edges with DNS headers; CNAME edges between FQDNs

 | ASN and netblock lookup | passive | AutonomousSystem, Netblock; announces, contains edges

 | Certificate transparency query | passive | TLSCertificate; common_name, san_dns_name edges to FQDN

 | HTTP probing | active | URL, Service, Product; domain, ip_address, port, product_used edges

 | Port scanning (rate-limited) | active | Service entities; port edges with port_number and protocol

 | TLS handshake | active | TLSCertificate; certificate edge from Service

 | WHOIS and RDAP | passive | DomainRecord, IPNetRecord, AutnumRecord, Organization; registration edges

Class assignments are defaults; a program can only tighten them.

## 7. The Flowforge language (DSL)

The DSL is a small, statically typed, expression-oriented language. It has immutable bindings, algebraic data types, pattern matching, closures, and effects that are tracked by the type checker. Source files use the extension .ff, are UTF-8, and have no preprocessor.

### 7.1 Example programs

// Declarations of registered tools are generated from the tool registry (section 6.2).
tool subfinder(domain: Fqdn)        -> Stream<Fqdn>         ! passive
tool resolve(name: Fqdn)            -> Option<IpAddress>    ! passive
tool httpx(host: InScope<Host>)     -> Option<HttpService> ! active

type HttpService = { url: Url, status: Int, title: Option<String>, tech: List<Product> }
type Report      = { new_assets: Int, alerts: Int }

#[timeout(2h)]
workflow recon(roots: List<Fqdn>) -> Report {
  let subs: Stream<Fqdn> = roots |> flat_map(subfinder) |> dedupe;
  let live = subs |> filter_map(resolve);                          // Stream<IpAddress>

  #[retry(max = 3, backoff = exp(1s, 30s))]
  let web = subs
    |> filter(n => scope.allows(n))                               // cheap passive filter
    |> par_map(n => httpx(scope.check(Host::Name(n))?), limit = 8)
    |> filter_map(x => x);

  for svc in web {
    match svc.tech |> first(p => p.name == "jenkins") {
      Some(p) => emit_alert(Severity::High, "Jenkins exposed: {svc.url}"),
      None    => (),
    }
  }
  Report { new_assets: len(web), alerts: 0 }
}

// ERP-style workflow with approval and compensation (saga)
tool extract_invoice(doc: DocRef) -> Invoice                       ! read
tool post_entry(e: LedgerEntry)    -> PostingId                    ! financial_write
tool reverse_entry(id: PostingId)  -> Unit                         ! financial_write

workflow post_invoice(doc: DocRef) -> Result<PostingId, String> {
  let inv = extract_invoice(doc);
  require approval(role = "finance_ap", reason = "post {inv.total} to ledger", timeout = 24h);
  let id = post_entry(entry_for(inv)) compensate reverse_entry(it);
  Ok(id)
}

// Agent step: the model proposes a plan as DSL source; the engine checks it before anything runs.
workflow triage(ctx: GraphSummary) -> Report {
  let plan: Plan<Report> = agent planner(
      goal    = "Probe newly discovered hosts that look like admin or CI systems",
      context = ctx,
      tools   = [resolve, httpx],
      budget  = Budget { tokens = 20000, tool_calls = 25, iterations = 3 });
  let result = execute(plan)?;        // plan was type-, effect- and scope-checked when produced
  result
}

### 7.2 Lexical grammar

 | Token | Definition

 | Whitespace | Space, tab, newline, carriage return. Not significant except to separate tokens.

 | Comments | // to end of line and nestable /* block */.

 | Identifier | [A-Za-z_][A-Za-z0-9_]*. Types, enum variants and records start with an uppercase letter by convention and by the checker's naming rule W0101.

 | Keywords | workflow fn tool type enum let for in match if else return require approval agent compensate true false as use

 | Integer | [0-9][0-9_]* and 0x[0-9a-fA-F_]+. 64-bit signed. Overflow is a compile error for literals and a run-time failure arith_overflow for operations.

 | Float | [0-9][0-9_]*\.[0-9][0-9_]*([eE][+-]?[0-9]+)?. IEEE 754 binary64. NaN is not producible by literals.

 | Duration | Integer followed by ms s m h d, for example 250ms, 2h. Stored as signed 64-bit nanoseconds.

 | String | "..." with escapes \n \t \" \\ \u{HEX}. {expr} inside a string interpolates the expression (it must have type String, Int, Float, Bool, Duration, Time, or a type with a built-in display). Use {{ and }} for literal braces.

 | Operators | + - * / % == != < <= > >= && || ! |> => -> ? . .. :: = : , ; ( ) [ ] { } # ! (the effect marker ! is the same token as logical not; the parser disambiguates by position).

### 7.3 Syntactic grammar (EBNF)

Notation: [ x ] optional, { x } zero or more, ( a | b ) choice, quoted text is a token. Expressions use precedence climbing (table below).

program      = { item } ;
item         = [ annotations ] ( workflow_decl | fn_decl | tool_decl | type_decl | enum_decl | use_decl ) ;
annotations  = { "#" "[" annotation { "," annotation } "]" } ;
annotation   = IDENT [ "(" [ arg { "," arg } ] ")" ] ;

use_decl     = "use" path ";" ;
path         = IDENT { "::" IDENT } ;

workflow_decl= "workflow" IDENT "(" [ params ] ")" [ "->" type ] [ effect ] block ;
fn_decl      = "fn" IDENT [ generics ] "(" [ params ] ")" [ "->" type ] [ effect ] block ;
tool_decl    = "tool" IDENT "(" [ params ] ")" "->" type effect ;          (* body-less: bound to registry *)
effect       = "!" IDENT { "," IDENT } ;                                    (* e.g. ! passive, financial_write *)
params       = param { "," param } ;
param        = IDENT ":" type ;
generics     = "<" IDENT { "," IDENT } ">" ;

type_decl    = "type" IDENT [ generics ] "=" "{" [ field { "," field } [ "," ] ] "}" ;
field        = IDENT ":" type ;
enum_decl    = "enum" IDENT [ generics ] "{" variant { "," variant } [ "," ] "}" ;
variant      = IDENT [ "(" type { "," type } ")" ] ;

type         = IDENT [ "<" type { "," type } ">" ]
             | "(" [ type { "," type } ] ")"                  (* tuple or unit *)
             | "(" [ type { "," type } ] ")" "->" type       (* function type *) ;

block        = "{" { stmt } [ expr ] "}" ;
stmt         = [ annotations ] let_stmt
             | for_stmt
             | require_stmt
             | "return" [ expr ] ";"
             | expr ";" ;
let_stmt     = "let" pattern [ ":" type ] "=" expr [ "compensate" expr ] ";" ;
for_stmt     = "for" pattern "in" expr block ;
require_stmt = "require" "approval" "(" [ arg { "," arg } ] ")" ";" ;

expr         = pipe ;
pipe         = or { "|>" or } ;
or           = and { "||" and } ;
and          = equality { "&&" equality } ;
equality     = relational [ ( "==" | "!=" ) relational ] ;
relational   = range [ ( "<" | "<=" | ">" | ">=" | "in" ) range ] ;
range        = additive [ ".." additive ] ;
additive     = multiplicative { ( "+" | "-" ) multiplicative } ;
multiplicative = unary { ( "*" | "/" | "%" ) unary } ;
unary        = ( "-" | "!" ) unary | postfix ;
postfix      = primary { "(" [ args ] ")" | "[" expr "]" | "." IDENT | "?" | "as" type } ;
primary      = literal | IDENT | path | "(" [ expr { "," expr } ] ")"
             | "[" [ expr { "," expr } ] "]"
             | record_lit | lambda | if_expr | match_expr | agent_expr | block ;
record_lit   = path "{" [ IDENT ":" expr { "," IDENT ":" expr } ] "}" ;
lambda       = ( IDENT | "(" [ IDENT { "," IDENT } ] ")" ) "=>" expr ;
if_expr      = "if" expr block [ "else" ( if_expr | block ) ] ;
match_expr   = "match" expr "{" arm { "," arm } [ "," ] "}" ;
arm          = pattern [ "if" expr ] "=>" expr ;
agent_expr   = "agent" IDENT "(" [ named_arg { "," named_arg } ] ")" ;
args         = arg { "," arg } ;
arg          = [ IDENT ( "=" | ":" ) ] expr ;
named_arg    = IDENT "=" expr ;

pattern      = "_" | IDENT | literal | path [ "(" pattern { "," pattern } ")" ]
             | "(" pattern { "," pattern } ")" | path "{" IDENT [ ":" pattern ] { "," ... } "}" ;
literal      = INT | FLOAT | STRING | DURATION | "true" | "false" ;

 | Level (low → high) | Operators | Associativity

 | 1 | |> | left; a |> f(x) means f(a, x), and a |> f means f(a)

 | 2 | || | left, short-circuit

 | 3 | && | left, short-circuit

 | 4 | == != | non-associative

 | 5 | < <= > >= in | non-associative

 | 6 | .. | non-associative (half-open integer range)

 | 7 | + - | left

 | 8 | * / % | left

 | 9 | unary - ! | right

 | 10 | call, index, field, ?, as | left

A lambda x => e extends as far right as possible. A block's final expression without a semicolon is its value; with a semicolon the block's value is ().

### 7.4 Types

 | Group | Types

 | Primitive | Int (i64), Float (f64), Bool, String (UTF-8), Duration, Time (Unix nanoseconds), Unit written ()

 | Composite | List<T>, Map<K, V> (K is String, Int or a domain scalar), Option<T> (Some, None), Result<T, E> (Ok, Err), Stream<T>, tuples, records, enums, function types

 | Domain (OAM-named) | Fqdn, IpAddress, Netblock, Asn, Url, Service, TlsCertificate, Product, Organization, and Host (built-in enum Name(Fqdn) | Ip(IpAddress)). Each is a distinct newtype validated on construction; there is no implicit conversion between them.

 | Scope | Scope (the pinned document), InScope<T> (proof that T passed scope.check), ScopeDenied (error record)

 | Engine | Plan<T>, Budget, Approval, Severity (enum Info | Low | Medium | High | Critical), RunInfo

Stream<T> in v0.1 is a materialized, ordered, chunked sequence produced by an effect. All list operations also work on streams. Laziness is not part of the language semantics.

### 7.5 Static semantics

- Name resolution: lexical scoping, bindings are immutable, shadowing in an inner block is allowed, redefinition in the same block is an error (E0202). Items are mutually visible in any order within a file.

- Type checking is bidirectional: literals, constructors and annotated parameters synthesize types; lambdas, empty lists and None are checked against an expected type. Generic functions use rank-1 parametric polymorphism with unification at the call site. No subtyping and no implicit coercions.

- Exhaustiveness: a match must cover all variants, or end with a wildcard. A pattern that can never match is a warning (W0501). Guards do not count toward exhaustiveness.

- The ? operator applies to Result<T, E> and Option<T>. In a function whose return type is Result<_, E2> the error type must be equal to E2 (no implicit conversion). In a workflow with a non-Result return, ? failing ends the run with status failed and code unwrap_failed.

- Effects: every expression has an effect set. A function's inferred effect set is the union of its body's. The declared set after !, when present, MUST be a superset of the inferred set (E0401); a declaration that is too broad is a warning (W0402). Calling a tool contributes the tool's declared effects. Effects are: read, passive, active, intrusive, write, financial_write, llm, time. The activity classes order as passive < active < intrusive.

- Scope typing: a tool parameter of type InScope<T> accepts only an expression of that type. The only ways to obtain one are scope.check(x: T) -> Result<InScope<T>, ScopeDenied> (an effect) and passing along a parameter that already has that type. An InScope<T> value cannot be stored in a record type declared outside the standard library, which prevents smuggling proofs across runs (E0302).

- Policy check (compile-time): for a program, the inferred effect set of a workflow is compared with the program's max_class; financial_write and intrusive require a reachable require approval or approve(...) before the first effect that uses them (E0403). The checker is told the program's policy; with no program it checks only internal consistency.

- Annotations: #[timeout(d)] on workflows and let-statements, #[retry(max = n, backoff = exp(initial, max))] on let-statements whose right side performs effects, #[idempotent] and #[deprecated("msg")] on items. Unknown annotations are errors (E0601).

- Compensation: let x = e compensate c; requires that e performs a write or financial_write effect; c is an expression evaluated with it bound to the value of x. Compensations run in reverse order of registration on failure or cancellation (section 9.6).

### 7.6 Standard library (pure unless marked)

 | Function | Type | Notes

 | map, filter, filter_map, flat_map | List<A> or Stream<A>, (A) -> B ...  | Closures may perform effects; evaluated sequentially in order.

 | par_map | (Stream<A>, (A) -> B, limit: Int) -> Stream<B> | Effect-aware concurrency; result order equals input order. Option on_error = fail | collect.

 | fold, any, all, first, count, len, take, skip, sort_by, group_by, dedupe, zip, enumerate, reverse, concat | usual | dedupe uses structural equality. sort_by is stable.

 | contains, starts_with, ends_with, split, join, trim, lower, upper, replace | String and List helpers | Unicode-aware, locale-independent.

 | parse_int, parse_float, to_string | conversions | Parsers return Option.

 | scope.allows(x) | (T) -> Bool | Local passive pre-filter using the pinned document (no effect, not a proof).

 | similar(e, k), embed(text) | (Entity, Int) -> List<Entity>, (String) -> Vector | Effects similarity_query and embed (section 22.9). Results are hints: pass them through scope.check before acting on them.

 | scope.check(x) | (T) -> Result<InScope<T>, ScopeDenied> | Effect scope_check. Records a decision.

 | approve(role, reason, timeout) | -> Result<Approval, Denied> | Effect. require approval(...) is sugar for approve(...)? with failure code approval_denied.

 | sleep(d), now() | Unit, Time | Effects (time); now() is recorded, so replay returns the original value.

 | emit_alert(sev, msg) | Unit | Effect; publishes a workflow_alert event.

 | execute(plan) | Plan<T> -> Result<T, PlanError> | Effect; runs an accepted plan as a child run.

 | log(level, msg) | Unit | Recorded as an event with a size cap.

## 8. Bytecode and virtual machine

### 8.1 Execution model

- A stack machine with a value stack, a call-frame stack and per-frame locals. Bindings are immutable, so closures capture by value and no upvalue closing is needed.

- Memory is managed per run: values are reference-counted immutable objects, or allocated in a per-run arena that is freed when the run ends. A tracing GC is not required by this specification.

- The VM is a pure function of (module, recorded effect results). It never reads clocks, randomness, the environment or the network.

- The VM runs until it completes, fails, exhausts fuel, or suspends on an effect:

run(state, fuel)  -> Suspended { seq, kind, args } | Completed { value } | Failed { code, message, span } | OutOfFuel
resume(state, effect_result: Ok(value) | Err(error_value)) -> same as run
snapshot(state)   -> bytes   (canonical CBOR, section 8.7)
restore(module, bytes) -> state

### 8.2 Values

 | Tag | Payload | Notes

 | Unit, Bool | none, 1 bit | 

 | Int, Duration, Time | i64 | Checked arithmetic; overflow raises arith_overflow.

 | Float | f64 | NaN results raise arith_nan. Equality is IEEE except NaN cannot occur.

 | String | UTF-8 bytes | Max 1 MiB.

 | List, Stream | vector of values | Max 1,000,000 elements. Stream is a list with a flag for display purposes.

 | Map | ordered map | Iteration order is insertion order; keys compared structurally.

 | Record | type id + field values | Fields in declaration order.

 | Enum | type id + variant index + payload values | Option and Result are enums with fixed type ids.

 | Closure | function id + captured values | 

 | Domain scalar | validated canonical string or bytes | Fqdn, IpAddress, Netblock, Asn, Url. Constructed only by validating builtins or tool results.

 | ScopeProof | type tag + canonical target + decision id | Runtime form of InScope<T>; not serializable into outputs.

 | EntityRef | entity id | Reference to a graph entity, resolved through effects only.

### 8.3 Module format

Little-endian binary. Section order is fixed. The module hash is the SHA-256 of the whole byte string and is stored with every run.

magic            "FFBC"                     4 bytes
format_version   u16                        // this document: 1
flags            u16
section CONSTS   u32 count, then (tag u8, len u32, bytes)       // ints, floats, strings
section TYPES    u32 count, then record and enum layouts        // names, fields, variants
section FUNCS    u32 count, then:
                   name_idx u32, arity u8, nlocals u16, ncaps u8,
                   code_len u32, code bytes,
                   span_table: (code_offset u32, source_offset u32, len u32)*
section EFFECTS  u16 declared effect mask, per-workflow
section TOOLS    u16 count, then (tool_name_idx u32, spec_sha256 32 bytes)*
section META     compiler_version, source_sha256, program_policy_sha256, workflow_name
entry            u16 function index of the workflow body

### 8.4 Instruction set

Operands follow the opcode. u8, u16 are unsigned little-endian; i32 is a signed jump offset relative to the next instruction.

 | Hex | Mnemonic | Operands | Stack effect and behavior

 | 00 | NOP |  | 

 | 01 | CONST | k:u16 | push constant k

 | 02-04 | UNIT, TRUE, FALSE |  | push

 | 05 | POP |  | discard top

 | 06 | DUP |  | duplicate top

 | 10 | LOAD_LOCAL | i:u16 | push local i

 | 11 | STORE_LOCAL | i:u16 | pop into local i (each local assigned once; verifier enforces)

 | 12 | LOAD_CAP | i:u8 | push captured value i of the current closure

 | 20-25 | ADD_I, SUB_I, MUL_I, DIV_I, MOD_I, NEG_I |  | checked i64; division by zero raises div_zero

 | 26-2A | ADD_F, SUB_F, MUL_F, DIV_F, NEG_F |  | f64

 | 2B | CONCAT |  | string concatenation

 | 30-35 | EQ, NE, LT, LE, GT, GE |  | structural comparison of two values of the same static type

 | 36 | NOT |  | boolean negation

 | 40 | JUMP | off:i32 | forward jump only

 | 41 | JUMP_IF_FALSE | off:i32 | pop bool; jump if false (also used for &&, || short-circuit)

 | 42 | LOOP | off:i32 | backward jump; the only backward jump; costs extra fuel

 | 50 | CALL | fn:u16, argc:u8 | push frame; args become locals

 | 51 | CALL_CLOSURE | argc:u8 | closure below args

 | 52 | RET |  | pop frame, push result

 | 53 | CLOSURE | fn:u16, ncaps:u8 | pop ncaps values, push closure

 | 60 | MAKE_LIST | n:u16 | pop n, push list

 | 61 | MAKE_MAP | n:u16 | pop 2n (key, value), push map

 | 62 | MAKE_REC | type:u16, n:u8 | pop n fields

 | 63 | GET_FIELD | f:u8 | record field by index

 | 64 | INDEX |  | list or map lookup; out of range raises index_oob

 | 65 | NEW_LIST |  | push empty builder list

 | 66 | LIST_PUSH |  | pop value, append to list below it

 | 67 | LIST_LEN |  | push length

 | 68 | LIST_GET |  | pop index, list; push element (unchecked after verified loop bounds)

 | 70 | MAKE_ENUM | type:u16, variant:u8, n:u8 | pop n payload values

 | 71 | TEST_VARIANT | variant:u8 | peek enum, push bool

 | 72 | UNPACK | n:u8 | pop enum, push its n payload values

 | 73 | TRY |  | if top is Err or None return it from the current function (or fail the run in a workflow body); else replace with payload

 | 78 | INTERP | n:u8 | pop n displayable values, push string

 | 80 | BUILTIN | id:u16, argc:u8 | pure native function; cost proportional to input size

 | 90 | EFFECT | kind:u8, argc:u8 | suspends the VM with Suspended{seq, kind, args}; on resume pushes the recorded result

 | 91 | PUSH_COMP | fn:u16, ncaps:u8 | register a compensation closure (with it bound at completion time)

 | F0 | HALT |  | complete with top of stack

 | F1 | FAIL | code:u16 | fail the run with a code from the failure table

Effect kinds for EFFECT: 1 tool_call, 2 scope_check, 3 approval, 4 sleep, 5 agent_call, 6 execute_plan, 7 emit_alert, 8 now, 9 log, 10 par_map, 11 embed (text, model id and version in; vector or blob reference out; recorded), 12 similarity_query (query and parameters in; ranked entity ids with the index watermark out; recorded).

### 8.5 Lowering rules (compiler obligations)

 | Source | Lowering

 | a |> f(x) | Desugared to f(a, x) at parse time.

 | e? | Evaluate e, then TRY.

 | match | Evaluate scrutinee into a temp local; for each arm TEST_VARIANT, JUMP_IF_FALSE to next arm, UNPACK and bind, evaluate guard (skip to next arm on false), evaluate body, JUMP to end. The checker guarantees exhaustiveness, so the final fall-through is FAIL match_failed and unreachable in verified code.

 | for x in xs { body } | NEW index local i = 0; LIST_LEN; loop: compare, JUMP_IF_FALSE to end, LIST_GET, bind, body, increment, LOOP.

 | map, filter, filter_map, flat_map | Same loop shape with a result builder (NEW_LIST, LIST_PUSH). Closures are inlined when they have no captures that escape, otherwise CALL_CLOSURE.

 | par_map(xs, f, limit) | One EFFECT par_map with args (list, closure, limit, on_error).

 | let x = e compensate c | Evaluate e and store x; build closure for c capturing x as it; PUSH_COMP.

 | require approval(...) | Evaluate args, EFFECT approval, TRY with failure code approval_denied.

 | String interpolation | Evaluate pieces, INTERP n.

### 8.6 Effect protocol, replay and parallelism

- On EFFECT, the VM stops with Suspended{ seq, kind, args }. seq is a per-run counter assigned by the VM, incremented at each effect in program order. Effects inside par_map children use a hierarchical id parent_seq/task_index/child_seq.

- The engine records effect_scheduled (with seq, kind, args_hash, canonical args) before it performs the effect, and effect_completed or effect_failed with the result afterwards.

- Replay: to rebuild state, start from the beginning (or the last snapshot) and, at each suspension, look up seq in the log. If found and the VM's args_hash matches, resume with the recorded result without performing the effect. If the hash differs, fail the run with nondeterminism_detected. If not found, this is the live frontier: perform the effect.

- par_map: the engine starts one child VM per element (up to limit concurrently), each running the closure with its own hierarchical effect ids. Results are joined in input order. With on_error = fail (default) the first failure cancels the siblings and the effect fails; with collect the result is List<Result<B, E>>.

- Non-deterministic inputs (now, agent output, tool results, approval decisions) enter only as recorded effect results. Randomness is not offered; use a recorded effect if needed.

### 8.7 Fuel, limits and snapshots

 | Item | Rule

 | Fuel | Each instruction costs 1; LOOP costs 5; EFFECT costs 50; BUILTIN costs 1 + n/16 where n is the total input element or byte count. Per-run limit set by the engine (default 50,000,000); agent plans execute with a smaller per-plan limit (default 5,000,000).

 | Limits | Value stack 65,536; call depth 256; live heap 64 MiB (counted by value size); string 1 MiB; list 1,000,000 elements; module 4 MiB; at most 10,000 effects per run unless the workflow declares #[effects(max = N)] up to 1,000,000.

 | Failure codes | arith_overflow, arith_nan, div_zero, index_oob, match_failed, unwrap_failed, approval_denied, scope_denied, effect_failed, timeout, budget_exceeded, out_of_fuel, nondeterminism_detected, limit_exceeded, cancelled

 | Snapshot | (module_hash, pc, frames[], stack[], compensation_stack[], next_seq, heap) encoded as deterministic CBOR (RFC 8949 section 4.2). A snapshot is a cache of replay: dropping all snapshots never changes behavior. Taken every 500 effects or 5 minutes, whichever is first.

### 8.8 Verifier (MUST run before load)

- All jump targets lie inside the function and on instruction boundaries. Only LOOP jumps backward.

- Abstract stack depth is the same on every path that reaches an instruction, never negative, and never above the function's declared maximum.

- Local indices are below nlocals; each local is written before read on every path and written at most once.

- Every function ends in RET, HALT or FAIL; no fall-through off the end.

- CALL arity equals the callee's; CONST, MAKE_REC, MAKE_ENUM indices exist; effect kinds are known.

- Every tool referenced has an entry in TOOLS whose spec_sha256 matches the registry at load time. A mismatch rejects the module (the tool changed since compile).

- Declared effect mask is a superset of the effects of all reachable EFFECT instructions.

## 9. Engine

### 9.1 Workflow lifecycle

- Register: submit .ff source for a workflow name. The engine runs the front end (lex, parse, resolve, type and effect check) and, when a program is given, the policy check (section 7.5, rule 7). The result is a list of diagnostics.

- Compile and verify: with no errors, produce a module (section 8.3) and run the verifier (section 8.8).

- Publish: stores an immutable workflow_version with source, module, module hash, inferred effect set and tool spec hashes. Versions are integers per workflow, assigned in order.

- Deprecate: blocks new runs from starting on that version; existing runs continue.

### 9.2 Run state machine

 | Status | Meaning | Enters from | Leaves to

 | pending | Submitted, not yet leased | submit | running, cancelled

 | running | A worker holds the lease and the VM is executing or an effect is in flight | pending, waiting, paused | waiting, paused, compensating, succeeded, failed, cancelling

 | waiting | Suspended on an effect that needs time: approval, timer, retry backoff, rate-limit delay | running | running, cancelling, failed (timeout)

 | paused | Stopped by a scope version change or kill switch; no effects execute | running, waiting | running, cancelling

 | cancelling | Cancel requested; in-flight effects are being cancelled | any non-terminal | compensating, cancelled

 | compensating | Running registered compensations in reverse order | running (on failure), cancelling | failed, cancelled

 | succeeded, failed, cancelled | Terminal. failed and cancelled carry compensation_outcome: none, completed or failed |  | none

Status is a projection of the event log and is also stored on the runs row for querying. If they disagree, the log wins and the row is repaired.

### 9.3 Event log

Each event is { run_id, seq, type, at, actor, payload }. seq starts at 1 and is gapless per run. actor is engine, vm, tool:<name>, or user:<id>.

 | Type | Payload (key fields)

 | run_submitted | workflow_version_id, program_id, scope_version, input, idempotency_key, submitted_by

 | run_started | module_sha256, fuel_limit

 | effect_scheduled | path, kind, args_hash, args

 | scope_decision | path, decision object (section 4.3)

 | effect_started | path, attempt, executor

 | effect_completed | path, result, duration_ms

 | effect_failed | path, attempt, error {code, message, retryable}

 | effect_retry_scheduled | path, attempt, retry_at

 | effect_outcome_unknown | path (a non-idempotent effect lost its executor mid-flight)

 | observation_ingested | path, observation_id, entity_count, edge_count

 | approval_requested | path, approval_id, role, reason, proposed, expires_at

 | approval_decided | approval_id, decision (approved | denied), actor, comment

 | approval_expired | approval_id

 | timer_started, timer_fired | path, fire_at

 | agent_call_recorded | path, model, prompt_ref, response_ref, tokens_in, tokens_out, latency_ms

 | plan_proposed, plan_accepted, plan_rejected | plan_id, source_sha256, diagnostics[] or module_sha256

 | child_run_started, child_run_finished | child_run_id, status

 | budget_exceeded | resource (tokens, tool_calls, requests, fuel), limit, used

 | scope_changed, run_paused, run_resumed | old_version, new_version, action; reason

 | compensation_started, compensation_step, compensation_finished | count; index, name, result; outcome

 | snapshot_taken | at_seq, snapshot_id

 | alert_emitted, log | severity, message; level, message (capped at 4 KiB)

 | run_cancel_requested, run_cancelled | actor, reason

 | run_succeeded, run_failed | output; code, message

### 9.4 Scheduling and single-writer guarantee

At most one worker advances a run at a time. The mechanism is a lease with a fencing token:

loop:
  run = SELECT ... FROM runs
        WHERE status IN ('pending','running','waiting') AND next_wake_at <= now()
          AND (lease_expires_at IS NULL OR lease_expires_at < now())
        ORDER BY tenant_fair_rank, priority DESC, next_wake_at
        LIMIT 1 FOR UPDATE SKIP LOCKED
  UPDATE runs SET lease_owner = me, lease_expires_at = now() + 30s, fence = fence + 1 RETURNING fence
  state = restore(latest snapshot) or fresh VM
  events = read events after snapshot.at_seq
  advance VM using replay rules (section 8.6)
  while VM suspends at live frontier:
      perform effect (9.5); every append uses:  INSERT INTO run_events ... WHERE runs.fence = :fence
      renew lease every 10s
  on VM completion/failure: append terminal event, release lease
  on wait (approval/timer): set next_wake_at, release lease

- An append whose fence no longer matches fails, and the old worker MUST stop immediately (it lost the lease).

- Fairness: tenant_fair_rank is a weighted round-robin position per tenant so one tenant's backlog cannot starve others. A per-tenant cap on concurrently running runs applies (default 20).

- Wakeups: a timer firing, an effect completing out of band, an approval decision, a cancel request, or a scope change all set next_wake_at = now() and emit a notification on the engine_wake channel (Postgres LISTEN/NOTIFY, or Pub/Sub) so workers need not poll quickly.

### 9.5 Executing effects

 | Kind | Behavior

 | scope_check | Call ScopeService.Check; record scope_decision; result is Ok(proof) or Err(ScopeDenied).

 | tool_call | Resolve the tool spec; verify InScope arguments have recorded allow decisions; call the limiter (section 14); call ToolRunner.Execute with an idempotency key; forward streamed observations to the graph; complete with the tool's declared output value.

 | approval | Create an approval row, record approval_requested, set the run waiting with next_wake_at = expires_at. A decision or expiry wakes the run.

 | sleep | Create a timer; wait.

 | agent_call | Assemble context (section 16), call the model, store prompt and response blobs, record agent_call_recorded; on a plan, compile and check it, then record plan_proposed and either plan_accepted or plan_rejected.

 | execute_plan | Start a child run on the accepted module, inheriting program, scope version and the remaining budget; complete when the child finishes.

 | par_map | Start child task VMs with hierarchical paths; join in input order.

 | emit_alert | Record alert_emitted and write an outbox event to run.events.

#### Retries

delay(n) = min(max_ms, initial_ms * multiplier^(n-1))         // n = failed attempts so far
wait    = random_uniform(0, delay(n))                          // "full jitter"
retry only if error.retryable and attempt < max_attempts and run deadline not passed

Errors are retryable when: transport unavailable, deadline exceeded, HTTP 429 or 5xx from a tool's upstream, and explicit tool-reported transient errors. Permanent: scope denied, validation errors, 4xx other than 429, budget exceeded. A rate-limit denial is not a failure: the engine waits retry_after and tries again without counting an attempt.

#### Idempotency and at-least-once execution

- Every effect has idempotency_key = hex(sha256(run_id || "/" || path)), stable across retries and across crashes. Tools that talk to external systems MUST pass it through.

- Tools marked idempotent: true may be re-executed after an ambiguous crash. For others, the engine records effect_outcome_unknown and moves the run to waiting until an operator resolves it, or the workflow declares #[on_unknown(retry)].

### 9.6 Compensation (saga)

- Each PUSH_COMP instruction pushes a closure onto the run's compensation stack (part of VM state and snapshots).

- On failure or cancellation, the engine appends compensation_started and runs the closures in reverse order, each as normal effects (recorded, retried, idempotent).

- If a compensation fails permanently, record compensation_step with the error, continue with the remaining ones, and set compensation_outcome = failed. Never abandon the stack silently.

- Compensations never receive new approval gates unless their own effect class requires one; the original approval stays valid for reversing the same action.

### 9.7 Approvals

- An approval is addressed to a role within the tenant (and optionally a program). Any user with that role and the permission approvals:decide may decide.

- The requester of the run MUST NOT approve their own run's approval when the run was started by a user (reason: self_approval). Runs started by schedules or service accounts have no such constraint.

- Decisions are idempotent per (approval, actor); the first decision wins; later attempts get 409.

- Expiry: at expires_at the approval becomes expired and the effect fails with approval_denied unless an escalation role was declared, in which case a new approval is created for that role.

### 9.8 Cancellation, timeouts, deadlines

- CancelRun appends run_cancel_requested. The worker cancels in-flight effects (runner streams get a cancel signal; adapters stop within 2 s), then runs compensations, then appends run_cancelled.

- #[timeout(d)] on a workflow sets a run deadline; on a let-statement it bounds that effect or block. Expiry fails with code timeout.

### 9.9 Crash recovery

- A leased run whose lease expired is picked up by any worker (section 9.4).

- The new worker restores the latest snapshot (if any), replays the events after it, and reaches the live frontier.

- For the effect at the frontier: if effect_started exists without a terminal event, treat as ambiguous (section 9.5). If only effect_scheduled exists, perform it.

### 9.10 Submit idempotency

SubmitRun requires an idempotency key. The pair (tenant, key) is unique. A repeat with the same request_hash returns the original run; a repeat with a different hash returns ALREADY_EXISTS reason IDEMPOTENCY_KEY_REUSED. Keys are retained for 7 days.

### 10.7 Operational rules

- Tenant isolation: every query filters on tenant_id. As defense in depth, enable row-level security on tenant-scoped tables with USING (tenant_id = current_setting('app.tenant_id')::uuid), and set that setting per transaction.

- Retention: run_events 400 days (archive to object storage as zstd JSON Lines before deleting a whole run); scope_decisions 13 months; snapshots keep the last 3 per run and delete when the run finishes; observations 90 days (raw blobs follow a bucket lifecycle rule); auth_audit 12 months.

- Migrations: forward-only, numbered, applied by a migration job before deploy; additive changes first, destructive changes in a later release.

- Search: search_text is maintained by the graph service on every upsert. Queries use search_text ILIKE '%q%' or similarity() with the trigram index; results are re-checked with an exact substring test when the query is 3 characters or longer.

## 11. gRPC contracts

### 11.1 Conventions

- Package flowforge.v1. One .proto per service plus common.proto and events.proto. Breaking changes go to v2; additive changes (new fields, new enum values) are allowed in v1.

- Every enum has a zero value named *_UNSPECIFIED. Field numbers are never reused; removed fields are reserved.

- Metadata (every call): authorization: Bearer <internal token>, x-tenant-id, x-actor (user:<id>, apikey:<id>, service:<name>), x-request-id, traceparent, optional idempotency-key. Tenant and actor are not message fields, so a client cannot spoof them in a body.

- Deadlines: every client call sets one. Defaults: unary 5 s, scope check 500 ms, streaming 10 min (with keep-alive 30 s).

- Pagination: page_size (default 50, max 500) and opaque page_token.

- Streaming resumption: watch streams take a cursor (after_seq) and send events in order, so a reconnect loses nothing.

 | Idempotency | Idempotency-Key: <uuid or opaque string, max 128>. Required on POST /runs; accepted on every POST. A replay returns the original status and body with header Idempotent-Replayed: true. Same key with a different body returns 409 IDEMPOTENCY_KEY_REUSED.

 | Pagination | Query page_size (1-500, default 50) and page_token. Response: { "items": [...], "next_page_token": "..." | null }.

 | Filtering | Plain query parameters (status=running, program_id=..., created_after=2026-11-01T00:00:00Z). Sorting by sort=-created_at where documented.

 | Concurrency | Updates to scope use base_version in the body (optimistic). Other PUT and PATCH accept If-Match: "<etag>".

 | Rate limits | Headers on every response: RateLimit-Limit, RateLimit-Remaining, RateLimit-Reset (seconds). A 429 adds Retry-After (seconds).

 | Tracing | Response header X-Request-Id. The client may send its own; the gateway generates one otherwise.

 | Unknown fields | Rejected with 400 VALIDATION_FAILED.

## 13. Authentication and authorization

### 13.1 Signup and verification

- POST /auth/signup creates a pending user, a tenant, and an owner membership. Response is always 202, even if the email already exists (do not reveal accounts); an existing user receives a "someone tried to sign up" email instead.

- Password policy: at least 12 characters, at most 128, checked against a breached-password list (k-anonymity API or local bloom filter). No composition rules.

- Hash with Argon2id, parameters at least memory 19 MiB, iterations 2, parallelism 1, 16-byte salt, 32-byte output; stored as a PHC string. Re-hash on login when parameters change.

- An email verification token is 32 random bytes, stored as SHA-256, valid 24 hours, single use. Login is refused for pending users.

- Throttles (limiter keys in section 14): signup per IP 5/hour; login per (IP) 20/10 min and per (email) 10/10 min; verification resend per user 3/hour. After 10 failures for an email, require a 15-minute cool-down; responses stay identical for unknown and known emails.

### 13.2 Tokens

 | Token | Format | Lifetime | Storage

 | Access | JWT, JWS compact, alg = EdDSA (Ed25519), header kid | 10 minutes | Client memory (API) or HttpOnly cookie (console). Never localStorage.

 | Refresh | 32 random bytes, base64url, prefix ffr_ | 30 days sliding, 90 days absolute | Server: SHA-256 hash in refresh_tokens. Client: HttpOnly; Secure; SameSite=Strict; Path=/v1/auth cookie, or secure storage for CLI.

 | API key | ffk_<key_id>_<32 random bytes base64url> | Optional expiry | Server: SHA-256 of the secret part; prefix stored in clear for lookup.

 | Internal | JWT, aud = flowforge-internal, minted by the gateway | 60 seconds | Memory only. Carries tenant, actor and role. Alternatively mTLS or Google ID tokens plus metadata (section 17).

{ "alg": "EdDSA", "typ": "JWT", "kid": "2026-11" }

  "iss": "https://api.flowforge.example",
  "aud": "flowforge-api",
  "sub": "usr_01JD8K0A",
  "tid": "ten_01JD8K0B",

  "sid": "ses_01JD8K0E",         // session (refresh family) id

}

### 13.3 Validation rules (every service that accepts a JWT)

- Reject unless alg is exactly the allowed algorithm (never trust the header to choose; none is invalid). Look up the key by kid in the cached JWKS (refresh on unknown kid, at most once per minute).

- Verify signature, then iss, aud, exp and iat with 30 seconds of clock skew allowance.

- Check revocation: Redis deny:jti:<jti> exists, or sv is lower than the cached session_version for the user (sv:<user_id> in Redis, TTL equal to access token lifetime).

- Take tid and role from the token only. Any tenant_id in a body or query that disagrees returns 404.

### 13.4 Refresh rotation with reuse detection

refresh(token):
  row = find by sha256(token)
  if row is none:                      return 401
  if row.revoked_at or row.expires_at < now:  return 401
  if row.used_at is set:               // a rotated token was presented again: theft suspected
      revoke every token in row.family_id; bump user.session_version; log auth_audit('refresh_reuse'); return 401
  mark row.used_at = now
  new = insert refresh_tokens(family_id = row.family_id, parent_id = row.id, expires_at = min(now+30d, family_start+90d))
  return new access token + new refresh token

### 13.5 Console sessions (cookies)

- Access token in cookie ff_at (HttpOnly; Secure; SameSite=Lax), refresh in ff_rt (SameSite=Strict, path /v1/auth).

- CSRF: state-changing requests from the console MUST carry a header X-CSRF-Token equal to a double-submit cookie ff_csrf (random per session, not HttpOnly). HTMX attaches it through hx-headers. Requests with a bearer header instead of cookies are exempt.

- Responses set Cache-Control: no-store on authenticated pages and Content-Security-Policy without inline script.

### 13.7 Key rotation

New signing key every 90 days. States: active (signs and verifies), retiring (verifies only, until the longest-lived token signed with it expires), retired. Private keys live in Secret Manager or KMS; the JWKS endpoint publishes only public keys with cache headers (max-age=300).

## 14. Rate limiting

Rate limiting protects targets (scope rules), upstream sources, and the platform. It is implemented as a library with a language-neutral contract and several algorithms, so implementations can be compared.

### 14.1 Contract

Limiter.acquire(key: string, cost: int = 1, now: Time) -> Result {
  allowed: bool,
  retry_after_ms: int,       // 0 if allowed
  remaining: int,            // best-effort
  limit: int
}
Limiter.configure(key_pattern, params)
// A "request" can acquire several keys atomically: Limiter.acquire_all([ (key, cost), ... ]).
// If any key denies, none is consumed, and retry_after_ms is the maximum of the denials.

Time is always an input, so every algorithm can be tested with deterministic clocks (section 19).

### 14.2 Algorithms

#### Token bucket

params: rate r (tokens/s), burst b
state:  tokens (float), last (time)
acquire(cost, now):
  tokens = min(b, tokens + (now - last) * r); last = now
  if tokens >= cost: tokens -= cost; return allowed
  return denied, retry_after = (cost - tokens) / r

#### GCRA (generic cell rate algorithm), the default

One timestamp of state per key (the theoretical arrival time, TAT), which makes it compact and suitable for atomics or a single Redis value.

params: emission interval T = 1/r, tolerance tau = (burst - 1) * T
state:  tat (time), initially 0
acquire(cost, now):
  inc     = T * cost
  base    = max(tat, now)
  new_tat = base + inc
  allow_at = new_tat - tau - T            // earliest time this request may pass
  if now < allow_at: return denied, retry_after = allow_at - now          // state unchanged
  tat = new_tat; return allowed, remaining = floor((tau + T - (new_tat - now)) / T)

#### Sliding window counter

params: limit L, window W
state:  count_current, count_previous, window_start
estimate = count_previous * (1 - elapsed_in_window / W) + count_current
allow if estimate + cost <= L; on window roll: previous = current, current = 0

#### Sliding window log (exact, memory heavy)

Keep timestamps of accepted requests in the last W; allow if the number is below L. Used as the accuracy baseline in benchmarks.

#### Leaky bucket (queue, shaping)

Requests enter a bounded FIFO and are released at rate r. Used where smooth pacing toward a target matters more than burst tolerance.

#### Adaptive limit (AIMD)

state: rate r (bounded by [r_min, r_max]); on every window of N requests:
  if any 429/timeout/5xx-rate > threshold in the window:  r = max(r_min, r * 0.5)       // multiplicative decrease
  else:                                                    r = min(r_max, r + a)         // additive increase (a = 0.1 * r_max)
  also honor Retry-After from the target by suspending acquires until then

#### Weighted fair queueing across tenants

each tenant i has weight w_i and virtual finish time F_i
on request of cost c at virtual time V:  start = max(V, F_i); F_i = start + c / w_i
serve the pending request with the smallest F; advance V to the start time of the one served

### 14.3 Hierarchy and keys

A tool call acquires all applicable keys atomically; the strictest wins.

 | Level | Key | Source of limit

 | Global | rl:g:<class> | Platform config

 | Tenant | rl:t:<tenant_id>:<class> | Plan

 | Program | rl:p:<program_id> | scope.activity.rate

 | Target | rl:h:<program_id>:<registrable domain or ip> | Program rate, divided if several tools target the same host

 | Tool | rl:tool:<tenant_id>:<tool> | ToolSpec rate

 | Auth endpoints | rl:auth:ip:<ip>:<endpoint>, rl:auth:acct:<sha256 email> | Section 13.1

 | API | rl:api:<tenant_id>:<route class> | Plan; surfaces as RateLimit headers

### 14.4 Distributed strategies

 | Strategy | How it works | Trade-off

 | Central (Redis) | A Lua script reads and writes the GCRA tat for all requested keys in one atomic call. Use Redis TIME as the clock so all nodes agree. | Exact, simple; adds a round trip and a dependency. On Redis failure: deny active work (fail closed), allow only local conservative limits for passive work.

 | Leased local budgets | A node leases a chunk of tokens (for example 10% of the burst) from the central store for a TTL (default 2 s) and spends it locally; unused budget returns on expiry. | Fewer round trips; can undershoot; bounded overshoot equals total outstanding leases.

 | CRDT counters | Each node keeps a G-counter of admitted requests per window; nodes gossip and merge by element-wise max; the sum is compared with the limit. | No central dependency; eventually accurate, can overshoot during partitions.

 | Consistent assignment | Hash the key (rendezvous hashing) to one owner node; callers forward there. | Exact and local on the owner; needs membership and forwarding.

-- KEYS: one or more limiter keys; ARGV: per key: T_ms, tau_ms, cost  (GCRA, atomic across keys)
local now = redis.call('TIME'); now = now[1] * 1000 + math.floor(now[2] / 1000)
local worst = 0
local news = {}
for i = 1, #KEYS do
  local T, tau, cost = tonumber(ARGV[3*i-2]), tonumber(ARGV[3*i-1]), tonumber(ARGV[3*i])
  local tat = tonumber(redis.call('GET', KEYS[i]) or '0')
  local new_tat = math.max(tat, now) + T * cost
  local allow_at = new_tat - tau - T
  if now < allow_at then worst = math.max(worst, allow_at - now) end
  news[i] = new_tat
end
if worst > 0 then return { 0, worst } end          -- denied; nothing written
for i = 1, #KEYS do
  local T, tau = tonumber(ARGV[3*i-2]), tonumber(ARGV[3*i-1])
  redis.call('SET', KEYS[i], news[i], 'PX', math.ceil(news[i] - now + tau + T))
end
return { 1, 0 }

### 14.5 Test vector (GCRA)

Params: rate 10/s so T = 100 ms; burst 5 so tau = 400 ms; initial tat = 0; each call has cost = 1. For each call, new_tat = max(tat, now) + T and allow_at = new_tat - tau - T; the call is denied when now < allow_at.

 | # | now (ms) | tat before | new_tat | allow_at | result | tat after

 | 1 | 0 | 0 | 100 | -400 | allowed | 100

 | 2 | 0 | 100 | 200 | -300 | allowed | 200

 | 3 | 0 | 200 | 300 | -200 | allowed | 300

 | 4 | 0 | 300 | 400 | -100 | allowed | 400

 | 5 | 0 | 400 | 500 | 0 | allowed | 500

 | 6 | 0 | 500 | 600 | 100 | denied, retry_after_ms = 100 | 500 (unchanged)

 | 7 | 100 | 500 | 600 | 100 | allowed | 600

So a burst of 5 passes immediately, the sixth waits 100 ms, and afterwards one request passes every 100 ms.

## 15. Notifications and alerts

### 15.1 Flow

- Services publish events to Pub/Sub (section 11.7). The notifier subscribes to graph.changes, run.events, approval.events, and auth.events.

- For each event it loads the tenant's enabled rules for the program, evaluates each rule, and for a match computes a dedupe_key, applies throttling, and creates an alert_event and one delivery per channel.

- A delivery worker sends with retries (exponential backoff with jitter: 10 s, 30 s, 2 min, 10 min, 1 h; give up after 24 h and mark failed). A failed channel never blocks other channels.

- Consumer idempotency: the notifier records (consumer, event_id) in processed_events in the same transaction that creates alerts.

### 15.2 Alert rule language

The rule language reuses the DSL expression grammar (section 7.3) for conditions and adds a small statement form.

alert_rule   = "alert" IDENT "when" expr "->" action { "," action } { clause } ;
action       = IDENT "(" [ arg { "," arg } ] ")" ;       (* slack("channel"), email("addr"), webhook("name") *)
clause       = "throttle" DURATION
             | "group_by" expr { "," expr }
             | "digest" DURATION
             | "severity" "=" IDENT
             | "quiet_hours" STRING ;                      (* e.g. "22:00-07:00 Asia/Kolkata" *)

Variables in scope in a rule: change (type, run_id, at, patch), entity (asset_type, content fields flattened, scope_status, confidence, state), edge, run, approval, event (type, tenant, program). Rules are pure and type-checked against the event schema; unknown fields are compile errors. Functions: contains, starts_with, ends_with, matches (RE2 syntax, size-limited), len, in.

alert new_admin_host
  when change.type == "entity_added" && entity.asset_type == "FQDN"
       && entity.scope_status == "in_scope" && entity.name matches "^(admin|jenkins|grafana)\\."
  -> slack("sec-recon"), email("lead@example.com")
  severity = High  throttle 1h  group_by entity.name

alert approval_waiting_long
  when event.type == "approval.requested" && approval.expires_at - event.occurred_at > 6h
  -> slack("approvals")  digest 15m

alert run_failed
  when event.type == "run.run_failed" -> webhook("pagerduty-bridge") severity = Critical

### 15.3 Semantics

- Dedupe key = sha256(rule_id || group_by values); throttle d suppresses further alerts for the same key within d (suppressed ones are stored with status suppressed and counted).

- digest d collects matches for d and sends one message with a count and the first 20 items.

- Quiet hours delay delivery of severities below High until the window ends. Critical ignores them.

- Rule compilation errors use the standard diagnostics format; a rule that fails to compile cannot be enabled.

 | email | { "provider_secret_ref": "sm://...", "from": "alerts@..." } | Plain text plus HTML; no secrets in the body.

 | webhook | { "url": "https://...", "secret_ref": "sm://..." } | HMAC-signed JSON (below). HTTPS only; destinations resolved and checked against a deny list of internal ranges (SSRF protection).

## 16. Agent flow

### 16.1 Loop

- Trigger: a schedule, a graph change matching a trigger rule, or a human goal.

- Context assembly (deterministic code): scope summary, graph summary (counts by type, the latest diff, top-N entities by rank), previous findings, remaining budget. Free-text fields that originated from targets are wrapped (16.3).

- Plan: the model returns a PlanProposal (16.2) containing DSL source.

- Compiler gate: lex, parse, type and effect check, policy check, scope typing, verifier. On errors, the diagnostics are returned to the model and it may repair, up to max_repairs (default 3).

- Policy gate: passive effects run automatically; active needs the program to allow it and, by default, an approval; intrusive and financial_write always need approval.

- Execute as a child run (section 9.5). Observations go to the graph.

- Observe: the model receives a structured digest of the child's result and the graph diff, never raw tool output.

- Triage: the model proposes ranks and annotations; the engine stores them as FlowforgeProperty tags with kind = hypothesis, unless the claim is backed by a tool observation, which is stored as fact by the ingest path, not by the model.

- Decide: stop or replan (section 16.5).

- Report: draft summary for human review.

### 16.3 Handling untrusted target content

- Anything collected from a target (HTTP bodies, titles, banners, certificate fields, DNS TXT, WHOIS text) is data. The model sees extracted, typed fields first. Free text is truncated to 256 characters, stripped of control characters, base64-wrapped or clearly delimited, and labeled as untrusted in the prompt.

- The system prompt states that untrusted text can contain instructions and MUST NOT be followed. This is a mitigation, not a control: the actual controls are structural (below).

- Structural controls: the model has no network or shell tool; its only output is DSL source; that source is checked by the compiler, effect checker, scope typing and policy gate; scope is enforced again at the engine, tool-runner and proxy; budgets are enforced by the engine.

### 16.4 Recording and replay

Every model call is an effect. The engine stores the prompt and the response in object storage and records agent_call_recorded (model, token counts, hashes, latency). On replay the recorded response is returned without calling the model. Prompts are versioned (prompt_version in the record). Temperature is 0 by default for planner calls.

### 16.5 Limits and termination

 | Limit | Default | Enforced by

 | Iterations (plan, execute, observe cycles) | 5 | Engine

 | Repairs per plan | 3 | Engine

 | Tokens per run | 20,000 (per program ceiling applies) | Engine; budget_exceeded event

 | Tool calls per run | 25 | Engine

 | Requests per target | From scope and limiter | Limiter and proxy

 | Plan fuel | 5,000,000 | VM

Stop when: budget spent, iteration cap reached, no new entity with rank above min_rank (default 0.5) after a cycle, goal condition met (workflow-defined predicate), or a human cancels.

### 16.6 Evaluation harness

- Record real runs (inputs, context, outputs). Replay them against a new prompt or model with the compiler and policy gate in the loop but without executing tools (tool results come from the recording).

- Metrics: plan validity rate (compiles within repairs), repair count, approval rejection rate, scope-denied proposals per plan, expected cost versus actual, relevant new assets per 1,000 tokens, false-lead rate from human labels.

- A change to a prompt or model ships only if validity and scope-violation metrics do not regress.

## 18. Observability and security checklist

### 18.1 Telemetry

- Logs: JSON, one line per event, fields ts, level, service, env, trace_id, span_id, request_id, tenant_id, run_id, effect_path, msg. No secrets, no tokens, no raw target payloads.

- Traces: W3C traceparent propagated through REST, gRPC metadata and Pub/Sub attributes; one span per effect, tool call, scope check and DB transaction.

- Metrics (examples): ff_runs_total{status}, ff_run_duration_seconds, ff_effects_total{kind,outcome}, ff_scope_decisions_total{decision,reason}, ff_limiter_denied_total{level}, ff_replay_nondeterminism_total, ff_agent_tokens_total, ff_agent_plan_rejected_total, ff_outbox_lag_seconds, ff_graph_ingest_seconds, ff_approvals_pending.

- SLO candidates: scope check p99 under 100 ms; run submit-to-start p95 under 5 s; graph ingest p95 under 1 s per observation; outbox lag p99 under 10 s.

### 18.2 Security checklist

- All inputs validated at the edge (schema) and again at the service (domain rules). Reject unknown fields.

- Per-tenant isolation tests: for every list and get endpoint, a test with two tenants proves no cross-read.

- Secrets only in Secret Manager; no secrets in env files, images, logs or events. Rotate signing keys (13.7).

- Webhook destinations validated against SSRF (no private ranges, no redirects to them).

- Dependencies pinned; images by digest; SBOM generated in CI; scanning blocks high severity findings.

- Tool sandboxes: non-root, read-only filesystem, no capabilities, CPU and memory limits, wall-clock timeouts, no credentials.

- Audit: every state-changing API call and every scope decision is logged with actor and request id; run events are immutable (10.4).

- Abuse controls: signup and login throttles, per-tenant quotas (runs per day, tokens per month, storage), global kill switch.

- Legal and policy: a program MUST have a scope document, and the product refuses to create runs against targets not covered by one. Users are responsible for operating only within programs they are authorized to test.

## 21. CSR graph snapshots and graph analytics

Postgres is the system of record for the graph (section 10.5). It is the wrong shape for whole-graph algorithms: PageRank or SCC over a join of entities and edges is pointer-chasing through B-trees. Analytics run on an immutable, in-memory Compressed Sparse Row (CSR) snapshot built from the system of record. The snapshot is a derived, disposable read model; it can always be rebuilt from Postgres.

### 21.1 Layout

One snapshot per (tenant_id, program_id). Nodes are renumbered to dense u32 indices 0..V-1; a side table maps index to entity id. A second, transposed CSR (incoming edges) is built alongside for reverse traversal and PageRank.

 | Array | Length | Type | Meaning

 | offsets | V + 1 | u64 (u32 if E < 2^32) | offsets[v]..offsets[v+1] is the slice of targets holding the out-neighbours of v. offsets[V] = E.

 | targets | E | u32 | Destination node index, sorted ascending within each row (enables binary search and sorted-merge intersection).

 | edge_label | E | u8 | Index into the label dictionary (section 5.5 relation labels).

 | edge_conf | E | u8 or f32 | Edge confidence, quantised 0..255 or stored as float.

 | node_type | V | u8 | Asset type code (section 5.4).

 | node_id | V | 16 bytes each | Entity UUID for index to id mapping. Reverse lookup via a sorted array or hash map built at load time.

 | in_offsets, in_sources, in_edge | V + 1, E, E | as above | Transposed CSR; in_edge[i] is the index of the forward edge, so attributes are not duplicated.

File format "FFCS" (little endian, all sections 64-byte aligned, mmap-friendly)
  header:   magic "FFCS" | version u16 | flags u16 | V u64 | E u64
            tenant_id 16B | program_id 16B | watermark_seq u64 | created_at i64
            section table: n u32, then n * { kind u16, offset u64, length u64, crc32c u32 }
  sections: 1 offsets | 2 targets | 3 edge_label | 4 edge_conf | 5 node_type | 6 node_id
            7 label_dict (count u16, then length-prefixed UTF-8 strings)
            8 in_offsets | 9 in_sources | 10 in_edge
  footer:   sha256 of everything above

Memory: about 8(V+1) + 4E + E + E bytes forward, plus 8(V+1) + 8E transposed.
        1M nodes and 10M edges is roughly 0.2 GB. Fits comfortably per program.

### 21.2 Building: counting sort in O(V + E)

build_csr(V, edges[(src, dst, label, conf)]):
  degree = [0; V]
  for e in edges: degree[e.src] += 1
  offsets = prefix_sum(degree) with a leading 0          // length V + 1
  cursor = copy of offsets[0..V]
  for e in edges:                                          // scatter
      i = cursor[e.src]; cursor[e.src] += 1
      targets[i] = e.dst; label[i] = e.label; conf[i] = e.conf
  for v in 0..V: sort row (targets, label, conf) by target // rows are short
  build transpose by running the same procedure with (dst, src)

Dense id assignment. Read entities ordered by entity_id, number them in that order, and keep the map. Because the order is deterministic, the same graph content yields the same snapshot bytes; the sha256 can therefore be compared across rebuilds.

### 21.3 Test vector

V = 5, edges (in input order) 0→1, 0→2, 1→3, 2→3, 3→4, 4→1.

degree  = [2, 1, 1, 1, 1]
offsets = [0, 2, 3, 4, 5, 6]
targets = [1, 2,  3,  3,  4,  1]       // row0 = [1,2], row1 = [3], row2 = [3], row3 = [4], row4 = [1]
in_offsets = [0, 0, 2, 3, 5, 6]        // in-degree = [0, 2, 1, 2, 1]
in_sources = [0, 4,  0,  1, 2,  3]     // incoming to 1: {0,4}; to 2: {0}; to 3: {1,2}; to 4: {3}

BFS from 0:      levels [0] [1,2] [3] [4]      dist = [0,1,1,2,3]
SCCs:            {0}  {2}  {1,3,4}             (cycle 1 -> 3 -> 4 -> 1; 2 cannot be re-entered)
Topological:     not a DAG (cycle exists); condensation DAG has 3 nodes
Weakly connected components: 1

### 21.4 Freshness: watermark, delta overlay, atomic swap

- Every graph mutation appends a row to graph.change_events with a monotonically increasing seq (per tenant). A snapshot records the watermark_seq it reflects.

- The graph service keeps a small in-memory delta overlay (added edges, removed edges, new nodes) for events with seq > watermark. Point queries (neighbours, BFS with small depth) consult snapshot plus overlay. Whole-graph analytics use the snapshot only and report the watermark in the response.

- Compaction triggers when the overlay exceeds 1% of E or 5 minutes elapse with a non-empty overlay: rebuild in the background from Postgres at a consistent seq, write to gs://.../snapshots/{tenant}/{program}/{watermark}.ffcs, then swap an Arc pointer (ArcSwap in Rust, atomic.Pointer in Go). Readers holding the old snapshot keep it until they finish.

- Stale or ageing entities (section 5.7) are excluded at build time using the configured stale_after; the exclusion rule is recorded in the header flags.

- Cold start: load the newest snapshot from GCS (mmap after download), replay change_events after its watermark into the overlay.

### 21.5 Algorithms

 | Algorithm | Used for | Details | Complexity

 | BFS, bounded depth | "What is reachable from this asset in N hops", blast radius, scope expansion preview | Frontier queue plus visited bitset; optional label filter; direction forward, reverse or both | O(V + E)

 | Dijkstra | Most-likely attack path between two assets | Edge cost -ln(confidence) (confidence in (0,1], so cost ≥ 0); binary heap with lazy deletion. Path confidence is exp(-cost). | O((V + E) log V)

 | PageRank | Rank assets by structural importance (hubs: shared CDNs, auth providers, mail gateways) | Damping 0.85, tolerance 1e-6 on L1 change, max 100 iterations, dangling mass redistributed uniformly; pull-based over the transposed CSR so each iteration is a parallel loop without atomics | O(k (V + E))

 | Connected components | Cluster assets into "estates" | Union-find with path halving and union by size over undirected view | O(E α(V))

 | Strongly connected components | Mutually reachable groups, cycle detection | Iterative Tarjan (explicit stack; recursion depth can reach V); output components in reverse topological order | O(V + E)

 | k-core | Densely interconnected core of the estate | Bucketed degree peeling (Batagelj-Zaversnik) | O(V + E)

 | Articulation points, bridges | Single assets whose loss disconnects an estate | Iterative low-link DFS over the undirected view | O(V + E)

 | Triangle count or common neighbours | Shared-infrastructure signals | Sorted-row intersection (merge or galloping) | O(E · dmax) worst case

All algorithms are pure functions of a snapshot plus parameters and are therefore easy to conformance test: golden outputs for the section 21.3 graph and for a set of generated graphs (path, star, cycle, grid, two cliques joined by a bridge) live in conformance/graph/*.json. PageRank results are compared with an absolute tolerance of 1e-5 and rank order.

## 22. Similarity search and DiskANN

Goal: answer "find assets like this one" and "find assets matching this free text" over millions of entities. Typical uses: lookalike phishing domains, other services running the same stack, clustering near-duplicate HTTP responses, grouping findings that describe the same weakness, suggesting related scope rules. Similarity is a hint: it never widens scope. Every result is passed through the scope service before it is returned or acted upon (section 4).

### 22.1 What gets embedded

 | Asset or object | Text or features fed to the model | Notes

 | FQDN | Name labels, resolved record types, hosting provider | Character n-gram features also feed SimHash (22.8)

 | Service | Banner or output, service_type, attributes | Truncate to 2 KiB before embedding

 | URL / HTTP response | Title, status, selected headers, first 4 KiB of body text | Near-duplicate pages cluster tightly

 | Finding (Vuln property) | Title and description | De-duplication of reports

 | Query text | The user's string | Must use the same model and version as the index

An embedding is produced by the recorded effect embed (kind 11, section 8.4): input text, model id and model version go in the effect request; the vector (or a content-addressed blob reference for it) is stored in the event log. Replay therefore returns the identical vector without calling the model. The graph service stores vectors in graph.embeddings; the model id, version and dimension are part of every row, and an index only mixes vectors of one (model_id, model_version).

### 22.2 Metrics

- L2: sum((a_i - b_i)^2) (skip the square root for ranking).

- Cosine: normalise vectors at insert time, then use inner product. Distance = 1 - dot(a, b).

- Inner product: distance = -dot(a, b).

The metric is fixed per index at creation. Distance kernels use SIMD (AVX2 or NEON) with a scalar fallback; the scalar version is the reference for tests.

### 22.3 Index architecture

                    queries                          writes (embedding upserts / deletes)
                       |                                        |
                       v                                        v
         +----------- searcher -----------+             +--- memtable ---+
         | fan out to all live segments,  |             | in-RAM graph,  |
         | merge top-k, drop tombstones,  |<------------| brute force    |
         | filter, optional re-rank       |             | below ~50k     |
         +-----+------------+-------------+             +-------+--------+
               |            |                                   | flush at N vectors
               v            v                                   v
        +-----------+ +-----------+  ...             +---------------------+
        | segment 1 | | segment 2 |  <---------------| background builder  |
        | DiskANN   | | DiskANN   |   immutable      | Vamana + PQ         |
        +-----------+ +-----------+                  +---------------------+
               ^
               +--- tombstone set (entity ids deleted or superseded) applied at query time
               +--- background merge: combine small segments, physically drop tombstoned vectors

- Memtable: recent vectors in memory. Below roughly 50,000 vectors use exact brute force; above that, an in-memory Vamana graph. Flushed to a segment at a size or age threshold.

- Segment: immutable DiskANN index file plus PQ codes. Written to local SSD, replicated to GCS for recovery.

- Tombstones: a delete or an update adds the old vector to the tombstone set; queries over-fetch (k * 2 then filter) to compensate.

- Merge: FreshDiskANN-style streaming merge. When tombstones exceed 20% of a segment, or the segment count exceeds 8, merge segments into a new one (insert new points with the Vamana insert, patch neighbours of deleted points, rebuild PQ if the codebook drifted). The old segments are deleted after the swap.

- Isolation: one index per (tenant_id, program_id, model_id). Small tenants share nothing; this removes filtered search from the hot path and makes erasure a file deletion. Cross-program queries within a tenant fan out over indexes.

### 22.4 Vamana graph construction

Parameters: R = 64 (max out-degree), L_build = 100 (search list), alpha = 1.2, metric d

build(points P):
  G = random R-regular directed graph on P            // initial connectivity
  s = medoid(P)                                       // closest point to the centroid
  for pass in [alpha = 1.0, alpha = alpha_final]:     // two passes
    for p in random_permutation(P):
      (_, V) = greedy_search(G, s, query = p, L = L_build)    // V = visited set
      N_out(p) = robust_prune(p, V, alpha, R)
      for j in N_out(p):                              // add backward edges
        N_out(j) = N_out(j) + {p}
        if |N_out(j)| > R: N_out(j) = robust_prune(j, N_out(j), alpha, R)

greedy_search(G, start, query, L):
  list = {start}; visited = {}
  while list has unvisited points:
    p* = closest unvisited point in list to query
    visited += p*
    list = list + N_out(p*)
    keep only the L closest points in list
  return (top-k of list, visited)

robust_prune(p, V, alpha, R):                         // diversify neighbours
  V = V - {p}; N_out = {}
  while V not empty:
    p* = argmin over V of d(p, v)
    N_out += p*
    if |N_out| == R: break
    remove from V every v with alpha * d(p*, v) <= d(p, v)
  return N_out

Intuition: RobustPrune keeps an edge to p* and discards candidates that p* already "covers" (they are at least a factor alpha closer to p* than to p). With alpha above 1 some longer edges survive, which shortens search paths at the cost of degree.

### 22.5 On-disk layout and search

Segment file, sector size 4096 B. Node record = { vector f32[dim] | degree u32 | neighbours u32[R] }
  dim = 768, R = 64: 3072 + 4 + 256 = 3332 B, padded so a record never straddles a sector
  node i lives at sector (i / records_per_sector), slot (i mod records_per_sector)
  header sector: magic "FFDA", version, dim, metric, R, V, medoid, pq params, tombstone epoch

In RAM per segment: PQ codes, m bytes per vector (for example m = 96 of 8-bit sub-codes for dim 768),
                    the PQ codebooks, and a copy of the medoid and a small cache of hot nodes
On SSD per segment: full-precision vectors and the adjacency lists

beam_search(query, k, L, W):                    // W = beam width, 4 is a good start
  lut = pq_distance_table(query)                // m x 256 table, one per query
  list = {medoid}, visited = {}, results = {}
  while list has unvisited points:
    B = up to W closest unvisited points in list
    read the sectors of B from SSD concurrently        // one round trip of I/O per iteration
    for p in B:
      results[p] = exact_distance(query, full_vector(p))   // free: vector is in the same sector
      for n in neighbours(p) not in visited-or-list:
        list += (n, pq_distance(lut, code[n]))          // approximate, from RAM
    keep the L closest list entries by approximate distance
    visited += B
  return the k points in results with the smallest exact distance

Product quantisation. Split each vector into m sub-vectors, run k-means with 256 centroids on each sub-space (train on a sample of 100k points), store one byte per sub-vector. Distance to a code is the sum of m table lookups. The exact re-rank uses the full vector that arrives with the node sector, so quality depends mostly on graph quality and L.

First version. Implement the interface (22.9) with pgvector (HNSW index, vector_cosine_ops) in the graph database. It is correct, filterable with SQL and enough for hundreds of thousands of vectors. The segmented DiskANN engine is a drop-in replacement behind the same interface and is justified by a measured need (RAM cost, latency, million-scale tenants).

### 22.6 Hybrid search: text plus vector

Run lexical search (the trigram index from section 5.9, or Postgres full-text) and vector search independently, then fuse the ranked lists with reciprocal rank fusion:

score(d) = sum over lists L of  1 / (60 + rank_L(d))        // rank starts at 1; absent from a list contributes 0
Example: d is rank 1 in lexical and rank 3 in vector:  1/61 + 1/63 = 0.01639 + 0.01587 = 0.03226
         e is rank 2 in lexical only:                  1/62        = 0.01613
         so d outranks e.

RRF needs no score normalisation between the two systems, which have incomparable scales.

### 22.7 Filters

Because indexes are per program, tenant and program filtering is structural. Remaining filters (asset type, tag, last_seen range) are applied after retrieval with over-fetching (k * 4, retry with larger L when fewer than k survive). Highly selective filters (fewer than 1% of points match) fall back to an exact scan of the matching ids fetched from Postgres.

### 22.8 Near-duplicate detection without embeddings

- SimHash (64-bit) over shingles of page text or banner tokens. Two documents are near duplicates when Hamming distance ≤ 3. Lookup uses multi-index hashing: split the 64 bits into 4 blocks of 16; any pair within distance 3 must match exactly on at least one block (pigeonhole), so query four hash tables and verify candidates with a popcount.

- MinHash + LSH for set similarity (for example sets of linked hostnames or certificate SANs): 128 permutations, 32 bands of 4 rows; the probability two sets with Jaccard s collide in at least one band is 1 - (1 - s^4)^32.

Both are cheap, need no model, and are deterministic, so they can run inside the VM as pure builtins.

## 23. Distributed systems design

Flowforge is distributed from day one: several instances of each service, workers that crash, Pub/Sub that redelivers. This section states the model and the rules so that every component makes the same assumptions. It also lays out an optional path from "Postgres is the source of truth" to a self-built replicated log, for learning purposes.

### 23.1 Failure model and assumptions

- Crash-stop with restart: processes may die at any instruction and later restart with durable state intact. Byzantine behaviour is out of scope.

- Network: messages can be delayed, duplicated, dropped or reordered; partitions occur and heal. Timeouts are the only failure detector, so they are unreliable by nature.

- Clocks: wall clocks skew and jump. Never use a wall clock to decide who owns something; use leases checked against a monotonic clock plus fencing tokens validated by the storage layer. Wall time is for display and for staleness heuristics only.

- Delivery: Pub/Sub, Cloud Tasks and gRPC retries are at-least-once. Every handler is idempotent.

- Principle: hashing and heartbeats are for efficiency (spread load, prefer a likely owner); leases with fencing are for safety (at most one effective writer). If hashing is wrong, work is merely duplicated or slow; if fencing is wrong, data is corrupt.

### 23.2 Guarantees by component

 | Component | Consistency | Under partition | Mechanism

 | Run event log | Linearizable per run (single writer, ordered seq) | Choose consistency: a minority side cannot append | Postgres transaction, expected_seq plus fencing token

 | Run ownership | At most one effective owner per run | Old owner is fenced when it next writes | Lease row, fence increments on every acquisition

 | Effect execution | At-least-once execution, exactly-once recording | May run twice; result recorded once | Idempotency key sha256(run_id/path), unique constraint on the result

 | Graph writes | Eventually consistent merge, convergent | Both sides accept writes, merge on heal | Commutative, associative, idempotent upserts (23.5)

 | Rate limits | Approximate, bounded error | Choose availability: local budgets continue (section 14.4) | Leased budgets, CRDT counters

 | Scope decisions | Fail closed | Deny when the scope store is unreachable and no fresh cache entry exists | Versioned scope documents, cache with short TTL

 | Alerts | At-least-once, de-duplicated | Delayed, never lost | Transactional outbox, inbox keyed by event id

 | Similarity index | Eventually consistent, watermark reported | Serves stale results | Idempotent upserts ordered by source_seq

In PACELC terms: the control plane (runs, approvals, scope) is PC/EC; the data plane (graph, search, rate limits) is PA/EL.

### 23.3 Work distribution

- Membership: workers write a heartbeat row (or Redis key with TTL) every 5 seconds; a worker is considered live for 15 seconds after its last heartbeat. A gossip protocol (SWIM-style, with suspicion) is the stretch goal.

- Rendezvous (highest-random-weight) hashing: for a key k and live workers w, the owner is argmax over w of hash(k, w). It needs no ring state and moves only the keys of a failed worker. Used for: run affinity (keep a run's VM snapshot hot), target affinity (a host's requests go through the same tool-runner, which makes per-target rate limits local and accurate).

- Consistent hashing with virtual nodes is the alternative when the key space needs weighting; keep both implementations behind a Placement trait and test them for balance and minimal movement.

- Claiming: the preferred owner tries to acquire the lease first; other workers delay their attempts by their rank in the hash order. If the preferred owner is dead, the next in line takes over after the lease expires. Ranks only change who tries first, never who may write.

- Back-pressure: worker concurrency is bounded by a semaphore per tenant and per tool class; the queue is the buffer; a full queue returns RESOURCE_EXHAUSTED with retry_after.

rendezvous_owner(key, workers):  // deterministic; every node computes the same answer from the same membership
  best = none
  for w in workers:
    score = hash64(key || w.id)          // for example xxh3 or siphash with a fixed key
    if best is none or score > best.score or (score == best.score and w.id < best.id): best = (w, score)
  return best.w

Test: 1000 keys over 5 workers, remove one worker: only keys owned by the removed worker move, roughly 200,
      and the remaining distribution stays within a few percent of uniform.

### 23.4 The EventStore abstraction

The engine depends on a narrow trait, so the implementation can change from Postgres to a replicated log without touching the VM or the engine logic.

// Specification-level signature (Rust shown; port the semantics to any language)
pub struct Fence(pub u64, pub u64);            // (term, counter); compared lexicographically

pub trait EventStore: Send + Sync {
    /// Append events if the stream head equals `expected_seq` AND `fence` is the current fence.
    /// Atomic. Returns the new head. Errors: SeqConflict, Fenced.
    async fn append(&self, run: RunId, expected_seq: u64, fence: Fence, events: &[Event])
        -> Result<u64, AppendError>;

    async fn read(&self, run: RunId, from_seq: u64, limit: usize) -> Result<Vec<Event>, StoreError>;
    async fn subscribe(&self, run: RunId, from_seq: u64) -> Result<EventStream, StoreError>;

    async fn save_snapshot(&self, run: RunId, at_seq: u64, bytes: Bytes) -> Result<(), StoreError>;
    async fn load_snapshot(&self, run: RunId) -> Result<Option<(u64, Bytes)>, StoreError>;

    /// Lease: returns a fence strictly greater than any previous fence for this run.
    async fn acquire_lease(&self, run: RunId, owner: WorkerId, ttl: Duration) -> Result<Lease, LeaseError>;
    async fn renew_lease(&self, lease: &Lease, ttl: Duration) -> Result<Lease, LeaseError>;
    async fn release_lease(&self, lease: Lease) -> Result<(), StoreError>;

    /// Runs that are ready for work: unleased or lease expired, with a due timer or pending event.
    async fn list_ready(&self, shard: Shard, limit: usize) -> Result<Vec<RunId>, StoreError>;
}

Properties every implementation must satisfy (these become the conformance suite in 23.8): (1) after a successful append at head h the next append must name expected_seq = h + n; (2) an append carrying an older fence fails even if expected_seq matches; (3) a read after a successful append observes it (read-your-writes) and reads are never reordered; (4) acquire_lease returns strictly increasing fences, including across restarts of the store.

#### Implementation A: Postgres (default)

The schema in section 10.4. append is a single transaction: SELECT ... FOR UPDATE on the run row, check head_seq = expected_seq AND fence = $fence, insert events, update head_seq. Lease acquisition does UPDATE runs SET fence = fence + 1, lease_owner = $w, lease_expires = now() + $ttl WHERE run_id = $r AND (lease_expires < now() OR lease_owner = $w) RETURNING fence. The now() here is the database clock, which is the single time source for lease expiry, so worker clock skew cannot break it. list_ready uses FOR UPDATE SKIP LOCKED.

#### Implementation B: sharded Raft log (optional, learning track)

- Sharding: shard = hash(run_id) mod S (S fixed at deployment, for example 64; resharding is done by splitting a shard's key range, not by changing S). Each shard is a Raft group of 3 or 5 replicas; the replicas of many shards share processes (multi-Raft) and share a transport.

- State machine: apply committed commands Append{run, expected_seq, fence, events}, AcquireLease, RenewLease, SaveSnapshot. The state machine is deterministic and checks expected_seq and fence at apply time, so a stale command from a deposed leader is rejected when it commits.

- Fence: (raft term, per-term counter). A new lease acquisition after a leader change always yields a larger term, which preserves strict monotonicity without a clock.

- Reads: ReadIndex (leader confirms leadership with a heartbeat round, waits for the applied index to reach the commit index at request time) for linearizable reads; follower reads allowed for subscribe with a lag bound.

- Log and snapshots: segmented write-ahead log with CRC per record and fsync policy (group commit); snapshot of the state machine every N applied entries, then truncate; install-snapshot RPC for slow followers.

- Membership change: single-server changes (one at a time) first; joint consensus as a stretch goal.

- Raft invariants to test: election safety (at most one leader per term), leader append-only, log matching, leader completeness, state machine safety.

- Deployment: replicas are stateful with persistent disks, so they need GKE StatefulSets (not Cloud Run). This is the main infrastructure reason Implementation B is optional.

### 23.5 Convergent graph merge

Several tool-runners and several pipelines write observations for the same entity concurrently. The merge function (section 5.7) is designed so the final state does not depend on arrival order or duplication:

 | Field | Merge rule | Commutative / associative / idempotent

 | created_at | min | yes / yes / yes

 | last_seen | max | yes / yes / yes

 | confidence | Noisy-or over distinct sources: 1 - prod(1 - c_i), with each source contributing at most once (keep the maximum per source) | yes / yes / yes (per-source max makes duplicates harmless)

 | tags and sources | Set union | yes / yes / yes

 | scalar attributes | Last-writer-wins by (observed_at, source_id) total order | yes / yes / yes

 | edges | Keyed by (from, label, to); upsert applies the rules above | yes / yes / yes

 | deletes | Never delete on observation; staleness (section 5.7) hides entities; explicit deletes are tombstones with a timestamp and win over older writes only | yes

Property tests: for random multisets of observations, applying them in any permutation, with arbitrary duplication, gives byte-identical graph state. This is the property that lets graph ingestion run at-least-once without coordination. In database terms it is an upsert INSERT ... ON CONFLICT DO UPDATE whose update expressions are exactly the table above.

### 23.6 Distributed queries and analytics

- Search and similarity: scatter-gather. The coordinator sends the query to every shard or segment, each returns its local top-k with distances, the coordinator merges with a k-way merge (heap), applies tombstones and filters, and returns. Hedged requests (send a duplicate to a second replica after the p95 latency) cut tail latency; deadlines propagate in gRPC metadata.

- Graph analytics at scale (stretch): partition the CSR by node range, run Pregel / bulk-synchronous-parallel supersteps (each worker processes its vertices, sends messages to neighbours, barrier, repeat). PageRank, connected components (label propagation) and BFS map directly onto it. Start single-process with a thread-per-partition runner and message queues, then move to processes. One snapshot per program fits in one machine for the foreseeable future, so this is for learning, not need.

### 23.7 Messaging and cross-service consistency

- Outbox: a service writes its state change and an outbox row in one transaction; a relay publishes to Pub/Sub and marks the row. A crash between publish and mark causes a duplicate, never a loss.

- Inbox: consumers record the event id in an inbox table inside the transaction that applies the effect; a duplicate hits the unique constraint and is acknowledged without effect.

- Ordering: Pub/Sub ordering keys per run or per entity where order matters; consumers still tolerate gaps by checking seq.

- No distributed transactions: cross-service workflows are sagas with compensation (section 9.6). Two-phase commit is explicitly not used.

- Dead letters: after N failed deliveries a message goes to a dead-letter topic with the failure reason; an operator tool replays or discards it.

- Distributed tracing: W3C traceparent in gRPC metadata and in Pub/Sub attributes, so one trace spans gateway, engine, tool-runner, graph and notifier.

### 23.8 Failure scenarios and how they are tested

 | Scenario | Expected behaviour | Invariant checked

 | Worker killed mid-run | Lease expires, another worker acquires a higher fence, replays the log, continues | Run completes; event log has no gaps or duplicate seq

 | Worker paused (GC, VM freeze) then resumes after losing its lease | Its next append fails with Fenced; it stops | No event from the stale owner is committed

 | Tool call succeeds, worker dies before recording the result | New owner re-issues the call with the same idempotency key | Tool sees one logical call; result recorded once

 | Pub/Sub redelivers an event 5 times | Inbox rejects duplicates | Alert sent once, graph merge unchanged

 | Partition between engine and Postgres | Appends fail; runs pause, nothing is lost | No partial state; resumes on heal

 | Redis unavailable | Limiters fall back to local budgets with reduced rate; fail closed for per-target active tools | Per-target rate never exceeds the configured ceiling

 | Scope store unreachable | Cached scope until TTL, then deny | No out-of-scope request leaves the egress proxy

 | Clock skew of 60 seconds on one worker | No effect on ownership (database clock); log timestamps flagged | No double ownership

 | Duplicate graph observations, any order | Same graph state | Convergence property (23.5)

 | Raft leader isolated (implementation B) | New leader elected; old leader's commands rejected after it steps down | No two committed values at one index

- Fault-injection harness: a test mode where every store, network and tool call passes through an adapter that can drop, delay, duplicate, reorder or fail it, driven by a seeded random generator. After each scenario run the invariant checker over the event logs: per-run seq contiguity, one writer per fence, idempotent effects, scope never violated, sagas complete or compensated.

- Linearizability check: record client-visible operation histories against the event store and verify them with a Wing and Gong style checker (or an existing tool such as Porcupine in Go, Knossos or Elle for the idea).

- Deterministic simulation testing (stretch): because the VM is already deterministic, run the whole cluster in one process with a simulated clock, simulated network and a seeded scheduler. Any failing seed reproduces exactly. This is the style used by FoundationDB and TigerBeetle; in Rust it pushes the design toward abstracting time, I/O and randomness behind traits from the start.

- Chaos in the cloud: kill Cloud Run instances, force Postgres failover, inject latency with the egress proxy, and re-run the invariant checker on the resulting logs.

### 23.9 Phases

 | Phase | Deliverable | Learning focus

 | D0 | Single process, Postgres EventStore, lease plus fence, idempotent effects, outbox/inbox | Correct single-writer under crashes

 | D1 | Multiple workers, rendezvous placement, heartbeats, back-pressure, fault-injection harness, invariant checker | Safety versus efficiency, testing distributed code

 | D2 | Scatter-gather search, hedged requests, convergent graph merge property tests, leased rate budgets | Tail latency, CRDT thinking

 | D3 | Raft library, single group on a simulated network, then multi-Raft EventStore on GKE StatefulSets | Consensus, snapshots, membership

 | D4 | Deterministic simulation of the whole cluster, Pregel-style partitioned analytics | Reproducible failure, bulk-synchronous computation

## 24. Modular architecture and module contracts

The system is built as a set of modules that can be implemented, tested and benchmarked one at a time, in isolation, in any order that respects the dependency rules. The style is clean (hexagonal, ports and adapters): a pure core with no I/O, surrounded by traits (ports) whose real implementations (adapters) live at the edge. A module is "done" only when it satisfies the definition in 24.6, which includes its tests and benchmarks.

### 24.1 Principles

- Pure core, effects at the edge. Domain logic (scope decision, DSL, VM, merge, limiters, CSR algorithms, distance kernels) takes values and returns values. It does not read the clock, generate randomness, touch the network or the disk, or log to a global.

- Ports only at real boundaries. A trait exists where a second implementation or a fake is needed (24.4). Do not wrap every struct in a trait.

- Every module ships with an in-memory fake of each port it exposes, so its consumers can be tested without Postgres, Redis or the network.

- Dependencies point inward and downward (24.3). No cycles. Enforced by a test that parses the package metadata (25.2, test arch/deps).

- Determinism. Given the same inputs and the same seed, a module produces the same outputs. Time and randomness come from ports.

- Services are thin. A service binary wires adapters to modules (gRPC handlers, config, telemetry). It contains no domain logic and has few tests of its own beyond wiring.

### 24.5 Isolation rules for implementers

- A module's tests MUST pass with only its own dependencies built (cargo test -p ff-scope never compiles Postgres drivers or tonic).

- Conformance data is read from conformance/<suite>/; a module never embeds expected values that also exist as data.

- No module reads environment variables, the system clock, or global state. Configuration arrives as a struct.

- Public API changes in a lower layer require updating the module's CHANGELOG entry and its conformance data version.

- Error types are per module (thiserror in Rust, sentinel errors in Go) and mapped to gRPC and REST codes only in services (section 11.8).

### 24.6 Definition of done for a module

An agent or a human may mark a module complete only when all of the following are true. cargo xtask verify-module <name> checks the mechanical items and fails otherwise.

- The public surface in 24.3 exists, is documented (/// on every public item), and has no unwrap() or expect() outside tests (Clippy lint unwrap_used denied).

- All required test cases for the module in 25.3 exist as tests whose names start with the case ids (for example scope_001_trailing_dot), and pass.

- All conformance suites listed for the module in modules.toml exist under conformance/ and pass.

- All property tests in 25.4 for the module exist and pass with 1,000 cases locally and 100,000 in the nightly job.

- Fuzz targets in 25.5 exist and run for 60 seconds without findings (nightly: 30 minutes).

- The benchmarks in 25.8 for the module exist, run with cargo bench -p <name>, and a baseline result file is committed under bench/results/<module>/.

- No forbidden dependency edge (arch/deps test passes); cargo clippy -- -D warnings and cargo fmt --check are clean.

- Any unsafe block is covered by a Miri test and carries a // SAFETY: comment stating the invariant.

- A short README.md in the module: purpose, the section of this spec it implements, how to run its tests and benchmarks, and known limitations.

### 25.2 Rules for all tests

- Deterministic. No wall-clock sleeps (use FakeClock), no real network in unit tests, no shared mutable global. A randomised test prints its seed on failure and accepts the seed through an environment variable (FF_SEED) to reproduce.

- Named by id. Required cases in 25.3 have stable ids; the test function starts with the id. xtask verify-module greps for them.

- Architecture test arch/deps. Parses cargo metadata, builds the module graph and asserts: layer rule from 24.3, no cycles, no adapter crate in a pure module's dependency tree, no std::time::SystemTime::now or Instant::now or rand::thread_rng usage in layer 0 to 4 crates (a simple source scan plus a Clippy disallowed_methods configuration).

- Every bug gets a regression test named regress_<issue>, ideally a conformance case.

- Coverage is a signal, not a target: report line and branch coverage (cargo llvm-cov); pure modules are expected to stay high, and a drop below the previous baseline needs an explanation in the PR. For ff-scope and ff-limiter also run mutation testing (cargo-mutants) nightly; surviving mutants in decision logic are treated as missing tests.

- No flaky tests. A test that fails intermittently is quarantined within a day and fixed or deleted within a week.

### 25.4 Property-based tests

 | Module | Property

 | ff-scope | normalize(normalize(x)) == normalize(x); check never panics for any string; adding a deny rule never turns a deny into an allow; removing an allow rule never turns a deny into an allow

 | ff-oam | Convergence: for any list of observations, any permutation and any duplication yield an identical graph state. Merge is commutative, associative and idempotent.

 | ff-limiter | For any timeline of requests, total allowed in any window [t, t + w] is at most burst + rate * w. All variants agree with a simple reference model (a list of timestamps) on generated timelines.

 | ff-csr | Build from a random edge list: degree sums equal E; each row sorted; transposed of transposed equals the original; BFS equals a naive adjacency-list BFS; Tarjan SCC equals a naive reachability-based SCC; PageRank equals a dense-matrix power iteration; snapshot plus overlay equals rebuild.

 | ff-dsl | Pretty-print then parse returns the same AST; generated well-typed programs always check; compiled program evaluated by the tree-walker equals the VM result.

 | ff-bytecode / ff-vm | Any module accepted by the verifier never causes a VM panic or stack error for any inputs; encode/decode identity; fuel accounting is monotonic.

 | ff-eventstore | Under random interleavings of append, lease and read from several simulated workers, per-run seq is contiguous and each fence value has one writer.

 | ff-engine | Crash at a random point, recover, continue: final event log equals the log of an uninterrupted run (up to timestamps).

 | ff-vecindex | Results are always a subset of live ids; distances are non-decreasing in the result list; after deleting everything, searches are empty; recall@k is monotonic non-decreasing in L on a fixed dataset (within tolerance).

 | ff-placement | Owner is a member of the live set; adding a worker only moves keys to the new worker.

proptest! {
    #![proptest_config(ProptestConfig::with_cases(1000))]
    #[test]
    fn oam_prop_merge_converges(obs in vec(arb_observation(), 0..60), seed in any::<u64>()) {
        let baseline = Graph::from_observations(&obs);
        let mut shuffled = obs.clone();

### 25.5 Fuzz targets

Invariants for every target: no panic, no undefined behaviour (run with sanitizers), no allocation beyond a limit, finishes within a time limit. A crashing input is committed to fuzz/corpus/regress/ and becomes a unit test.

 | Target | Input | Extra check

 | fuzz_lexer, fuzz_parser | Arbitrary bytes as source | On success, pretty-print and re-parse gives the same AST

 | fuzz_checker | Structured (grammar-aware) programs | Diagnostics have spans inside the source

 | fuzz_bytecode_decode, fuzz_verifier | Arbitrary bytes as a module | If verified, running it with small fuel never panics

 | fuzz_snapshot_decode | Arbitrary bytes as a CBOR snapshot | Rejected or loads and runs safely

 | fuzz_scope_normalize | Arbitrary strings as target | Idempotent; never matches a rule it should not (compare against a slow reference matcher)

 | fuzz_jwt | Arbitrary token strings | Never accepted without a valid signature

 | fuzz_rest_json | Arbitrary request bodies per endpoint | Always a defined 4xx, never a 5xx

 | fuzz_csr_open, fuzz_segment_open | Arbitrary bytes as file | Clean error; no out-of-bounds read (also under Miri on small inputs)

 | fuzz_alert_rule | Arbitrary rule text | Diagnostics or a rule; never a panic

### 25.6 Differential tests

- Tree-walking evaluator versus bytecode VM (every vm/run case plus generated programs).

- Naive reference versus optimised implementation: CSR algorithms versus adjacency-list versions; GCRA/atomic version versus the timestamp-list model; SIMD versus scalar kernels; rendezvous versus a slow recomputation.

- Exact versus approximate: BruteForceIndex versus DiskANN and versus pgvector (recall, not equality).

- Implementation versus implementation: MemStore versus Postgres versus Raft behind the EventStore conformance suite.

- Language versus language: Go reference and Rust port run the same conformance/ data and must produce identical outputs (section 20.2).

### 25.7 Simulation and invariants

ff-sim runs the engine, several workers, the event store, a fake tool executor, a fake scope service and a fake Pub/Sub inside one process, with every call going through an adapter that can drop, delay, duplicate, reorder or fail it, and with a simulated clock. A scenario is (seed, fault_profile, workload). After the run, check_invariants(history) must return no violations:

 | Id | Invariant

 | inv_01 | Per run, event seq is contiguous from 1 with no duplicates.

 | inv_02 | Each fence value has at most one writer, and fences strictly increase over time.

 | inv_03 | No event is committed by a writer whose fence was already superseded.

 | inv_04 | Every tool effect has at most one recorded result; the tool executor may have run it more than once only with the same idempotency key.

 | inv_05 | Replaying a run's log reproduces its terminal state and its effect order.

 | inv_06 | No active tool call was issued for a target without a prior allow decision in the same run for that target and scope version.

 | inv_07 | Every saga that failed has either completed compensation in reverse order or is marked as needing operator action.

 | inv_08 | Every alert-worthy event produced exactly one delivered alert per rule and dedupe window (duplicates in the transport do not produce duplicate alerts).

 | inv_09 | The graph state after the simulation equals the state obtained by applying the set of recorded observations once each in a canonical order.

 | inv_10 | Per-target request rate observed by the fake tool executor never exceeds the configured ceiling over any window.

 | inv_11 | Every submitted run reaches a terminal state, or is still non-terminal only because the workload ended (liveness within a bounded number of simulated seconds after faults stop).

Fault profiles: none, crashy (workers killed at random instants), lossy (drop and duplicate messages), slow (random latency spikes), partitioned (workers cut from the store for intervals), skewed (clock offsets), and a chaos mix. CI runs 200 seeds per profile per PR and 10,000 nightly; a failing seed is printed and added to conformance/sim/regress_seeds.json.

### 25.8 Benchmarks

Methodology (applies to all).

- Micro benchmarks use criterion (statistical, with warm-up and outlier reporting); where CI noise is a problem also record instruction counts (iai-callgrind or perf stat) because they are stable across machines.

- Macro benchmarks live in bench/ and use a purpose-built load generator (open-loop with a target rate, to avoid coordinated omission). They report throughput and latency percentiles p50, p90, p99, p99.9 from an HDR histogram.

- Fixed seeds and generated datasets (xtask gen-bench-data) so any two runs use identical inputs. External datasets (SIFT1M, GIST1M) are downloaded by script, never committed.

- Record the environment in every result: CPU model, cores, RAM, OS, kernel, rustc version, build profile (--release with lto = "thin", codegen-units = 1), commit, and whether the CPU governor was pinned.

- Results format: one JSON file per run under bench/results/<module>/<date>-<commit>.json with {bench_id, params, metrics: {name: value, unit}, env}; xtask bench-compare <baseline> <new> prints deltas.

- Targets are measured, then fixed. The first run of each benchmark produces the baseline. Acceptance thresholds below are expressed as shapes and ratios (scaling, speed-ups, recall floors) that can be checked without guessing absolute numbers; absolute budgets are set after the baseline and recorded in bench/budgets.toml.

- Regression gate: nightly compares against the stored baseline; a regression of more than 10% in a stable metric (instruction counts) or 20% in a timing metric, sustained over three runs, opens an issue. A PR that deliberately slows something updates the baseline with a stated reason.

- Every benchmark also tracks allocations per operation (dhat or a counting allocator) because accidental allocation in hot paths is the most common regression.

### 25.11 CI stages

- Fast (every push): fmt, clippy -D warnings, cargo deny (licences, advisories), arch/deps, unit and conformance tests, property tests at 1,000 cases, loom tests, snapshot tests.

- Integration (every PR): Postgres, Redis and the Pub/Sub emulator through testcontainers; adapter and service tests; EventStore suite against Postgres; 200 simulation seeds; 60-second fuzz smoke.

- Nightly: property tests at 100,000 cases, 30-minute fuzz per target, Miri on unsafe modules, sanitizers (address, thread), mutation testing on ff-scope and ff-limiter, 10,000 simulation seeds across all fault profiles, full benchmark suite with comparison to the baseline, coverage report.

- Post-deploy to dev: end-to-end script, the system benchmarks b_sys_*, and a chaos run that kills workers and forces a Postgres failover, followed by the invariant checker over the exported logs.

### 25.12 Guidance for a coding agent

- Work on one module at a time in the order of 24.7. Start by reading the module's section, its row in 24.3, its test table in 25.3 and its modules.toml entry.

- Write the test list and the conformance data first (they will fail), then implement until they pass. Do not edit expected values to make a test pass without a written justification that cites this specification.

- When this specification is ambiguous or inconsistent (for example fields flagged verify), do not guess silently: add a docs/open-questions.md entry in the module, pick the most conservative behaviour (fail closed for anything touching scope), and add a test that pins the choice.

- Finish by running cargo xtask verify-module <name> and cargo xtask bench-module <name>, commit the baseline result, and summarise: what was implemented, what the benchmark showed, what remains.

- Never weaken a safety invariant (scope, fencing, idempotency, determinism) to improve a benchmark.
