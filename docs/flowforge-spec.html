Flowforge Specification

A language-agnostic design for Flowforge, a durable workflow engine with a typed DSL, a bytecode VM and agent steps, and Sentinel, the scope-enforced asset graph it feeds. The graph model follows the OWASP Amass Open Asset Model (OAM).

2. System overview

2.1 Purpose

Flowforge runs workflows written in a typed DSL. A workflow orchestrates tools (recon tools, ERP actions, LLM calls) as durable, replayable effects. Sentinel stores what the tools learn as a graph of assets and relations. A program's scope bounds everything: no tool may touch a target that scope does not allow.

2.2 Glossary

TenantAn account boundary. All data and quotas are per tenant.

2.3 Goals and non-goals

GoalsDurable runs that survive crashes and replay deterministically. A typed DSL where scope and effects are visible to the compiler. A graph compatible with OAM. Per-tenant isolation. Human approval for risky actions. Full audit of every decision.
Non-goals (v0.1)General-purpose programming. Running untrusted native code. Exploit execution. Multi-region active-active. A hosted marketplace of tools.

2.4 Invariants

These MUST hold in every implementation.
  1. Scope: no active or intrusive tool call executes unless the scope service allowed that exact normalized target under the run's scope version, and the decision is in the event log.
  2. Determinism: given the same bytecode and the same recorded effect results, the VM reaches the same state. The VM has no clock, randomness or I/O of its own.
  3. Append-only log: run events are never updated or deleted during a run's life. State is derived from them.
  4. Agents propose, the engine disposes: an agent can only emit DSL source. Type, effect, scope and policy checks run outside the model.
  5. Tenant isolation: no query, cache key or event crosses a tenant boundary.
  6. No silent success: an unreachable scope service, rate limiter or policy engine means deny, not allow.

3.2 Communication rules

  • gRPC (HTTP/2, TLS) for request/response and streaming between services. Every call carries metadata authorization (internal token), x-tenant-id, x-request-id, traceparent, and an optional idempotency-key. Every call sets a deadline.
  • Pub/Sub for fan-out events. Producers write events to an outbox table in the same transaction as the state change; a relay publishes them at-least-once. Consumers MUST be idempotent, keyed by event_id.
  • Only gateway is reachable from the internet. Internal services trust the gateway's internal token, never a client-supplied identity.
  • tool-runner has no direct internet access. Its only route out is the scope-checked egress proxy.

3.3 Life of a run

  1. Client calls POST /v1/runs with a workflow version, inputs and Idempotency-Key. The gateway authenticates, authorizes, and forwards SubmitRun.
  2. Engine pins the current scope version, loads bytecode, records run_submitted, and schedules the run.
  3. A scheduler worker leases the run, loads recorded events, and drives the VM until it suspends on an effect.
  4. For a tool effect the engine calls scope.Check, records scope_decision, then ToolRunner.Execute. The runner re-checks scope per target and streams observations.
  5. Engine records effect_completed and forwards observations to graph.IngestObservations. Graph writes entities and edges, computes changes, and emits graph.changes.
  6. Notifier evaluates alert rules on those changes. Agent and approval effects follow the same record-then-act pattern.
  7. When the VM returns, the engine records run_succeeded or run_failed, and the final state is derived from the log.

FieldRules
rules[].kinddomain (exact name), wildcard_domain (*. prefix; matches any depth below the name, never the apex itself), cidr (IPv4 or IPv6 prefix), url_prefix (scheme, host, port and path prefix on a segment boundary), asn (value AS64500, allowed only as informational input to discovery, never as sole permission for active work).
rules[].effectallow or deny. Deny always wins over allow. No match means deny.
activity.max_classHighest activity class any run of this program may perform. A workflow whose inferred effect exceeds this fails the compile-time policy check and is also refused at run time.
activity.rateProgram-level ceiling, enforced by the limiter (section 14) in addition to tenant and tool limits.
activity.windowsAllowed testing windows. Outside a window only passive effects may run; active ones wait.
versionMonotonic integer. A run is pinned to one version. Publishing a new version pauses in-flight runs of that program at their next effect boundary and re-validates them.

4.2 Normalization (MUST run before any match)

  1. Domain names: trim, lowercase, remove one trailing dot, convert to IDNA A-label (punycode), reject empty labels, reject names longer than 253 octets or labels longer than 63.
  2. URLs: parse; lowercase scheme and host; strip default ports (:80, :443); drop fragment; reject userinfo (credentials in URL) for scope decisions; percent-decode unreserved characters; collapse . and .. path segments.
  3. IP addresses: parse strictly (no octal, hex or decimal-integer IPv4 forms); output canonical text; map IPv4-mapped IPv6 to IPv4.
  4. Anything that fails to normalize yields decision deny with reason invalid_target.

4.3 Decision algorithm

function check(target, class, scope, now) -> Decision
  t = normalize(target)                       // section 4.2
  if t is invalid:                            return deny("invalid_target")
  if class > scope.activity.max_class:        return deny("class_exceeds_program")
  if class != passive and not in_window(now): return deny("outside_window")
  for rule in scope.rules where rule.effect == deny:
      if matches(rule, t): return deny("explicit_deny", rule.id)
  if class != passive and t is hostname:
      ips = resolve_once(t)                   // pinned for the connection that follows
      for ip in ips:
          for rule in scope.rules where rule.effect == deny and rule.kind == cidr:
              if matches(rule, ip): return deny("resolved_ip_denied", rule.id)
  for rule in scope.rules where rule.effect == allow:
      if matches(rule, t): return allow(rule.id, pinned_ips=ips)
  return deny("no_matching_allow")

A decision is { decision, reason, rule_id, scope_version, target, pinned_ips[], decided_at }. The same object is stored in the scope_decisions table and the run's event log.

4.5 Edge cases the implementation MUST handle

  • Redirects and CNAME chains: re-run check on every hop. A redirect to an out-of-scope host is not followed.
  • Check-then-use race: connect only to pinned_ips from the allow decision. Never re-resolve between check and connect.
  • Shared hosting and CDNs: permission attaches to the hostname rule, never to an IP alone.
  • URL tricks: https://acme.com@evil.com/, https://acme.com.evil.com/, mixed case, trailing dot, punycode lookalikes, IPv6 zones, decimal IPs. All covered by normalization plus host-only matching.
  • Scope changes mid-run: see version semantics above.

5. Graph model (Open Asset Model aligned)

5.1 Principles

  • The graph stores entities (nodes holding one OAM asset), edges (typed, directed relations between entities) and tags (properties attached to an entity or an edge). This mirrors the OAM and its asset-db library, where each of these also carries created_at and last_seen.
  • Asset and relation type names, labels and field names use OAM names so that data can be exported to or imported from Amass-compatible tooling.
  • Flowforge adds tenant, program, scope status, confidence, provenance and lifecycle columns around the OAM content (tagged ff). They never change the meaning of the OAM content.
  • OAM assets are JSON documents. The graph keeps them as a jsonb column plus a canonical key used for de-duplication.

5.7 Ingest and merge semantics

  1. Resolve: for each entity in an observation compute key. Upsert by (tenant, program, asset type, key). If new, set created_at = last_seen = observed_at. If existing, set last_seen = max(last_seen, observed_at) and merge content with non-empty wins, newest wins on conflict.
  2. Edges: upsert by (from_entity, to_entity, relation type, label, relation discriminator), where the discriminator is port_number+protocol for port relations and rr_type for DNS relations.
  3. Provenance: add one SourceProperty per (tool, entity or edge). Confidence from several independent sources combines as 1 - Π(1 - cᵢ), where each cᵢ is the highest confidence reported by one source, and is capped at 0.99.
  4. Scope status: computed by calling the same matcher as section 4 in passive mode (no resolution). Unknown is never promoted to in-scope by inference.
  5. Staleness: an entity becomes stale when the sources that previously reported it completed a covering run (same tool, same input) and did not report it for stale_after_runs (default 3) consecutive runs. It becomes active again when seen. Nothing is hard-deleted; deletion is an explicit admin action recorded in the audit log.
  6. Change events are produced in the same transaction through the outbox, one per effective change: entity_added, entity_changed (with a JSON patch), entity_stale, entity_reactivated, edge_added, edge_removed (stale), scope_status_changed.

6.3 Adapter contract

  1. An adapter implements: spec() → ToolSpec, and run(input, ctx) → stream of Observation.
  2. The adapter MUST NOT open network connections itself except through the proxy provided in ctx.
  3. It MUST stream results as they are produced (batches of at most 500 entities), and MUST stop within 2 seconds of a cancel signal.
  4. It MUST normalize values with the functions in section 4.2 before emitting entities, so keys match across tools.
  5. It reports progress as { items_done, items_total? } and structured errors with a retryable flag.

7. The Flowforge language (DSL)

The DSL is a small, statically typed, expression-oriented language. It has immutable bindings, algebraic data types, pattern matching, closures, and effects that are tracked by the type checker. Source files use the extension .ff, are UTF-8, and have no preprocessor.

7.5 Static semantics

  1. Name resolution: lexical scoping, bindings are immutable, shadowing in an inner block is allowed, redefinition in the same block is an error (E0202). Items are mutually visible in any order within a file.
  2. Type checking is bidirectional: literals, constructors and annotated parameters synthesize types; lambdas, empty lists and None are checked against an expected type. Generic functions use rank-1 parametric polymorphism with unification at the call site. No subtyping and no implicit coercions.
  3. Exhaustiveness: a match must cover all variants, or end with a wildcard. A pattern that can never match is a warning (W0501). Guards do not count toward exhaustiveness.
  4. The ? operator applies to Result<T, E> and Option<T>. In a function whose return type is Result<_, E2> the error type must be equal to E2 (no implicit conversion). In a workflow with a non-Result return, ? failing ends the run with status failed and code unwrap_failed.
  5. Effects: every expression has an effect set. A function's inferred effect set is the union of its body's. The declared set after !, when present, MUST be a superset of the inferred set (E0401); a declaration that is too broad is a warning (W0402). Calling a tool contributes the tool's declared effects. Effects are: read, passive, active, intrusive, write, financial_write, llm, time. The activity classes order as passive < active < intrusive.
  6. Scope typing: a tool parameter of type InScope<T> accepts only an expression of that type. The only ways to obtain one are scope.check(x: T) -> Result<InScope<T>, ScopeDenied> (an effect) and passing along a parameter that already has that type. An InScope<T> value cannot be stored in a record type declared outside the standard library, which prevents smuggling proofs across runs (E0302).
  7. Policy check (compile-time): for a program, the inferred effect set of a workflow is compared with the program's max_class; financial_write and intrusive require a reachable require approval or approve(...) before the first effect that uses them (E0403). The checker is told the program's policy; with no program it checks only internal consistency.
  8. Annotations: #[timeout(d)] on workflows and let-statements, #[retry(max = n, backoff = exp(initial, max))] on let-statements whose right side performs effects, #[idempotent] and #[deprecated("msg")] on items. Unknown annotations are errors (E0601).
  9. Compensation: let x = e compensate c; requires that e performs a write or financial_write effect; c is an expression evaluated with it bound to the value of x. Compensations run in reverse order of registration on failure or cancellation (section 9.6).

8. Bytecode and virtual machine

8.1 Execution model

  • A stack machine with a value stack, a call-frame stack and per-frame locals. Bindings are immutable, so closures capture by value and no upvalue closing is needed.
  • Memory is managed per run: values are reference-counted immutable objects, or allocated in a per-run arena that is freed when the run ends. A tracing GC is not required by this specification.
  • The VM is a pure function of (module, recorded effect results). It never reads clocks, randomness, the environment or the network.
  • The VM runs until it completes, fails, exhausts fuel, or suspends on an effect:
run(state, fuel)  -> Suspended { seq, kind, args } | Completed { value } | Failed { code, message, span } | OutOfFuel
resume(state, effect_result: Ok(value) | Err(error_value)) -> same as run
snapshot(state)   -> bytes   (canonical CBOR, section 8.7)
restore(module, bytes) -> state

8.6 Effect protocol, replay and parallelism

  1. On EFFECT, the VM stops with Suspended{ seq, kind, args }. seq is a per-run counter assigned by the VM, incremented at each effect in program order. Effects inside par_map children use a hierarchical id parent_seq/task_index/child_seq.
  2. The engine records effect_scheduled (with seq, kind, args_hash, canonical args) before it performs the effect, and effect_completed or effect_failed with the result afterwards.
  3. Replay: to rebuild state, start from the beginning (or the last snapshot) and, at each suspension, look up seq in the log. If found and the VM's args_hash matches, resume with the recorded result without performing the effect. If the hash differs, fail the run with nondeterminism_detected. If not found, this is the live frontier: perform the effect.
  4. par_map: the engine starts one child VM per element (up to limit concurrently), each running the closure with its own hierarchical effect ids. Results are joined in input order. With on_error = fail (default) the first failure cancels the siblings and the effect fails; with collect the result is List<Result<B, E>>.
  5. Non-deterministic inputs (now, agent output, tool results, approval decisions) enter only as recorded effect results. Randomness is not offered; use a recorded effect if needed.

8.8 Verifier (MUST run before load)

  1. All jump targets lie inside the function and on instruction boundaries. Only LOOP jumps backward.
  2. Abstract stack depth is the same on every path that reaches an instruction, never negative, and never above the function's declared maximum.
  3. Local indices are below nlocals; each local is written before read on every path and written at most once.
  4. Every function ends in RET, HALT or FAIL; no fall-through off the end.
  5. CALL arity equals the callee's; CONST, MAKE_REC, MAKE_ENUM indices exist; effect kinds are known.
  6. Every tool referenced has an entry in TOOLS whose spec_sha256 matches the registry at load time. A mismatch rejects the module (the tool changed since compile).
  7. Declared effect mask is a superset of the effects of all reachable EFFECT instructions.

9. Engine

9.1 Workflow lifecycle

  1. Register: submit .ff source for a workflow name. The engine runs the front end (lex, parse, resolve, type and effect check) and, when a program is given, the policy check (section 7.5, rule 7). The result is a list of diagnostics.
  2. Compile and verify: with no errors, produce a module (section 8.3) and run the verifier (section 8.8).
  3. Publish: stores an immutable workflow_version with source, module, module hash, inferred effect set and tool spec hashes. Versions are integers per workflow, assigned in order.
  4. Deprecate: blocks new runs from starting on that version; existing runs continue.

9.4 Scheduling and single-writer guarantee

At most one worker advances a run at a time. The mechanism is a lease with a fencing token:

loop:
  run = SELECT ... FROM runs
        WHERE status IN ('pending','running','waiting') AND next_wake_at <= now()
          AND (lease_expires_at IS NULL OR lease_expires_at < now())
        ORDER BY tenant_fair_rank, priority DESC, next_wake_at
        LIMIT 1 FOR UPDATE SKIP LOCKED
  UPDATE runs SET lease_owner = me, lease_expires_at = now() + 30s, fence = fence + 1 RETURNING fence
  state = restore(latest snapshot) or fresh VM
  events = read events after snapshot.at_seq
  advance VM using replay rules (section 8.6)
  while VM suspends at live frontier:
      perform effect (9.5); every append uses:  INSERT INTO run_events ... WHERE runs.fence = :fence
      renew lease every 10s
  on VM completion/failure: append terminal event, release lease
  on wait (approval/timer): set next_wake_at, release lease
  • An append whose fence no longer matches fails, and the old worker MUST stop immediately (it lost the lease).
  • Fairness: tenant_fair_rank is a weighted round-robin position per tenant so one tenant's backlog cannot starve others. A per-tenant cap on concurrently running runs applies (default 20).
  • Wakeups: a timer firing, an effect completing out of band, an approval decision, a cancel request, or a scope change all set next_wake_at = now() and emit a notification on the engine_wake channel (Postgres LISTEN/NOTIFY, or Pub/Sub) so workers need not poll quickly.

Retries

delay(n) = min(max_ms, initial_ms * multiplier^(n-1))         // n = failed attempts so far
wait    = random_uniform(0, delay(n))                          // "full jitter"
retry only if error.retryable and attempt < max_attempts and run deadline not passed

Errors are retryable when: transport unavailable, deadline exceeded, HTTP 429 or 5xx from a tool's upstream, and explicit tool-reported transient errors. Permanent: scope denied, validation errors, 4xx other than 429, budget exceeded. A rate-limit denial is not a failure: the engine waits retry_after and tries again without counting an attempt.

Idempotency and at-least-once execution

  • Every effect has idempotency_key = hex(sha256(run_id || "/" || path)), stable across retries and across crashes. Tools that talk to external systems MUST pass it through.
  • Tools marked idempotent: true may be re-executed after an ambiguous crash. For others, the engine records effect_outcome_unknown and moves the run to waiting until an operator resolves it, or the workflow declares #[on_unknown(retry)].

9.6 Compensation (saga)

  1. Each PUSH_COMP instruction pushes a closure onto the run's compensation stack (part of VM state and snapshots).
  2. On failure or cancellation, the engine appends compensation_started and runs the closures in reverse order, each as normal effects (recorded, retried, idempotent).
  3. If a compensation fails permanently, record compensation_step with the error, continue with the remaining ones, and set compensation_outcome = failed. Never abandon the stack silently.
  4. Compensations never receive new approval gates unless their own effect class requires one; the original approval stays valid for reversing the same action.

9.7 Approvals

  • An approval is addressed to a role within the tenant (and optionally a program). Any user with that role and the permission approvals:decide may decide.
  • The requester of the run MUST NOT approve their own run's approval when the run was started by a user (reason: self_approval). Runs started by schedules or service accounts have no such constraint.
  • Decisions are idempotent per (approval, actor); the first decision wins; later attempts get 409.
  • Expiry: at expires_at the approval becomes expired and the effect fails with approval_denied unless an escalation role was declared, in which case a new approval is created for that role.

9.8 Cancellation, timeouts, deadlines

  • CancelRun appends run_cancel_requested. The worker cancels in-flight effects (runner streams get a cancel signal; adapters stop within 2 s), then runs compensations, then appends run_cancelled.
  • #[timeout(d)] on a workflow sets a run deadline; on a let-statement it bounds that effect or block. Expiry fails with code timeout.

9.9 Crash recovery

  1. A leased run whose lease expired is picked up by any worker (section 9.4).
  2. The new worker restores the latest snapshot (if any), replays the events after it, and reaches the live frontier.
  3. For the effect at the frontier: if effect_started exists without a terminal event, treat as ambiguous (section 9.5). If only effect_scheduled exists, perform it.

9.10 Submit idempotency

SubmitRun requires an idempotency key. The pair (tenant, key) is unique. A repeat with the same request_hash returns the original run; a repeat with a different hash returns ALREADY_EXISTS reason IDEMPOTENCY_KEY_REUSED. Keys are retained for 7 days.

10.7 Operational rules

  • Tenant isolation: every query filters on tenant_id. As defense in depth, enable row-level security on tenant-scoped tables with USING (tenant_id = current_setting('app.tenant_id')::uuid), and set that setting per transaction.
  • Retention: run_events 400 days (archive to object storage as zstd JSON Lines before deleting a whole run); scope_decisions 13 months; snapshots keep the last 3 per run and delete when the run finishes; observations 90 days (raw blobs follow a bucket lifecycle rule); auth_audit 12 months.
  • Migrations: forward-only, numbered, applied by a migration job before deploy; additive changes first, destructive changes in a later release.
  • Search: search_text is maintained by the graph service on every upsert. Queries use search_text ILIKE '%q%' or similarity() with the trigram index; results are re-checked with an exact substring test when the query is 3 characters or longer.

11.1 Conventions

  • Package flowforge.v1. One .proto per service plus common.proto and events.proto. Breaking changes go to v2; additive changes (new fields, new enum values) are allowed in v1.
  • Every enum has a zero value named *_UNSPECIFIED. Field numbers are never reused; removed fields are reserved.
  • Metadata (every call): authorization: Bearer <internal token>, x-tenant-id, x-actor (user:<id>, apikey:<id>, service:<name>), x-request-id, traceparent, optional idempotency-key. Tenant and actor are not message fields, so a client cannot spoof them in a body.
  • Deadlines: every client call sets one. Defaults: unary 5 s, scope check 500 ms, streaming 10 min (with keep-alive 30 s).
  • Pagination: page_size (default 50, max 500) and opaque page_token.
  • Streaming resumption: watch streams take a cursor (after_seq) and send events in order, so a reconnect loses nothing.

13. Authentication and authorization

13.1 Signup and verification

  1. POST /auth/signup creates a pending user, a tenant, and an owner membership. Response is always 202, even if the email already exists (do not reveal accounts); an existing user receives a "someone tried to sign up" email instead.
  2. Password policy: at least 12 characters, at most 128, checked against a breached-password list (k-anonymity API or local bloom filter). No composition rules.
  3. Hash with Argon2id, parameters at least memory 19 MiB, iterations 2, parallelism 1, 16-byte salt, 32-byte output; stored as a PHC string. Re-hash on login when parameters change.
  4. An email verification token is 32 random bytes, stored as SHA-256, valid 24 hours, single use. Login is refused for pending users.
  5. Throttles (limiter keys in section 14): signup per IP 5/hour; login per (IP) 20/10 min and per (email) 10/10 min; verification resend per user 3/hour. After 10 failures for an email, require a 15-minute cool-down; responses stay identical for unknown and known emails.

13.3 Validation rules (every service that accepts a JWT)

  1. Reject unless alg is exactly the allowed algorithm (never trust the header to choose; none is invalid). Look up the key by kid in the cached JWKS (refresh on unknown kid, at most once per minute).
  2. Verify signature, then iss, aud, exp and iat with 30 seconds of clock skew allowance.
  3. Check revocation: Redis deny:jti:<jti> exists, or sv is lower than the cached session_version for the user (sv:<user_id> in Redis, TTL equal to access token lifetime).
  4. Take tid and role from the token only. Any tenant_id in a body or query that disagrees returns 404.

14. Rate limiting

Rate limiting protects targets (scope rules), upstream sources, and the platform. It is implemented as a library with a language-neutral contract and several algorithms, so implementations can be compared.

14.1 Contract

Limiter.acquire(key: string, cost: int = 1, now: Time) -> Result {
  allowed: bool,
  retry_after_ms: int,       // 0 if allowed
  remaining: int,            // best-effort
  limit: int
}
Limiter.configure(key_pattern, params)
// A "request" can acquire several keys atomically: Limiter.acquire_all([ (key, cost), ... ]).
// If any key denies, none is consumed, and retry_after_ms is the maximum of the denials.

Time is always an input, so every algorithm can be tested with deterministic clocks (section 19).

14.2 Algorithms

Token bucket

params: rate r (tokens/s), burst b
state:  tokens (float), last (time)
acquire(cost, now):
  tokens = min(b, tokens + (now - last) * r); last = now
  if tokens >= cost: tokens -= cost; return allowed
  return denied, retry_after = (cost - tokens) / r

GCRA (generic cell rate algorithm), the default

One timestamp of state per key (the theoretical arrival time, TAT), which makes it compact and suitable for atomics or a single Redis value.

params: emission interval T = 1/r, tolerance tau = (burst - 1) * T
state:  tat (time), initially 0
acquire(cost, now):
  inc     = T * cost
  base    = max(tat, now)
  new_tat = base + inc
  allow_at = new_tat - tau - T            // earliest time this request may pass
  if now < allow_at: return denied, retry_after = allow_at - now          // state unchanged
  tat = new_tat; return allowed, remaining = floor((tau + T - (new_tat - now)) / T)

Sliding window counter

params: limit L, window W
state:  count_current, count_previous, window_start
estimate = count_previous * (1 - elapsed_in_window / W) + count_current
allow if estimate + cost <= L; on window roll: previous = current, current = 0

Sliding window log (exact, memory heavy)

Keep timestamps of accepted requests in the last W; allow if the number is below L. Used as the accuracy baseline in benchmarks.

Leaky bucket (queue, shaping)

Requests enter a bounded FIFO and are released at rate r. Used where smooth pacing toward a target matters more than burst tolerance.

Adaptive limit (AIMD)

state: rate r (bounded by [r_min, r_max]); on every window of N requests:
  if any 429/timeout/5xx-rate > threshold in the window:  r = max(r_min, r * 0.5)       // multiplicative decrease
  else:                                                    r = min(r_max, r + a)         // additive increase (a = 0.1 * r_max)
  also honor Retry-After from the target by suspending acquires until then

Weighted fair queueing across tenants

each tenant i has weight w_i and virtual finish time F_i
on request of cost c at virtual time V:  start = max(V, F_i); F_i = start + c / w_i
serve the pending request with the smallest F; advance V to the start time of the one served

15. Notifications and alerts

15.1 Flow

  1. Services publish events to Pub/Sub (section 11.7). The notifier subscribes to graph.changes, run.events, approval.events, and auth.events.
  2. For each event it loads the tenant's enabled rules for the program, evaluates each rule, and for a match computes a dedupe_key, applies throttling, and creates an alert_event and one delivery per channel.
  3. A delivery worker sends with retries (exponential backoff with jitter: 10 s, 30 s, 2 min, 10 min, 1 h; give up after 24 h and mark failed). A failed channel never blocks other channels.
  4. Consumer idempotency: the notifier records (consumer, event_id) in processed_events in the same transaction that creates alerts.

15.2 Alert rule language

The rule language reuses the DSL expression grammar (section 7.3) for conditions and adds a small statement form.

alert_rule   = "alert" IDENT "when" expr "->" action { "," action } { clause } ;
action       = IDENT "(" [ arg { "," arg } ] ")" ;       (* slack("channel"), email("addr"), webhook("name") *)
clause       = "throttle" DURATION
             | "group_by" expr { "," expr }
             | "digest" DURATION
             | "severity" "=" IDENT
             | "quiet_hours" STRING ;                      (* e.g. "22:00-07:00 Asia/Kolkata" *)

Variables in scope in a rule: change (type, run_id, at, patch), entity (asset_type, content fields flattened, scope_status, confidence, state), edge, run, approval, event (type, tenant, program). Rules are pure and type-checked against the event schema; unknown fields are compile errors. Functions: contains, starts_with, ends_with, matches (RE2 syntax, size-limited), len, in.

alert new_admin_host
  when change.type == "entity_added" && entity.asset_type == "FQDN"
       && entity.scope_status == "in_scope" && entity.name matches "^(admin|jenkins|grafana)\\."
  -> slack("sec-recon"), email("lead@example.com")
  severity = High  throttle 1h  group_by entity.name

alert approval_waiting_long
  when event.type == "approval.requested" && approval.expires_at - event.occurred_at > 6h
  -> slack("approvals")  digest 15m

alert run_failed
  when event.type == "run.run_failed" -> webhook("pagerduty-bridge") severity = Critical

15.3 Semantics

  • Dedupe key = sha256(rule_id || group_by values); throttle d suppresses further alerts for the same key within d (suppressed ones are stored with status suppressed and counted).
  • digest d collects matches for d and sends one message with a count and the first 20 items.
  • Quiet hours delay delivery of severities below High until the window ends. Critical ignores them.
  • Rule compilation errors use the standard diagnostics format; a rule that fails to compile cannot be enabled.

16. Agent flow

16.1 Loop

  1. Trigger: a schedule, a graph change matching a trigger rule, or a human goal.
  2. Context assembly (deterministic code): scope summary, graph summary (counts by type, the latest diff, top-N entities by rank), previous findings, remaining budget. Free-text fields that originated from targets are wrapped (16.3).
  3. Plan: the model returns a PlanProposal (16.2) containing DSL source.
  4. Compiler gate: lex, parse, type and effect check, policy check, scope typing, verifier. On errors, the diagnostics are returned to the model and it may repair, up to max_repairs (default 3).
  5. Policy gate: passive effects run automatically; active needs the program to allow it and, by default, an approval; intrusive and financial_write always need approval.
  6. Execute as a child run (section 9.5). Observations go to the graph.
  7. Observe: the model receives a structured digest of the child's result and the graph diff, never raw tool output.
  8. Triage: the model proposes ranks and annotations; the engine stores them as FlowforgeProperty tags with kind = hypothesis, unless the claim is backed by a tool observation, which is stored as fact by the ingest path, not by the model.
  9. Decide: stop or replan (section 16.5).
  10. Report: draft summary for human review.

16.3 Handling untrusted target content

  • Anything collected from a target (HTTP bodies, titles, banners, certificate fields, DNS TXT, WHOIS text) is data. The model sees extracted, typed fields first. Free text is truncated to 256 characters, stripped of control characters, base64-wrapped or clearly delimited, and labeled as untrusted in the prompt.
  • The system prompt states that untrusted text can contain instructions and MUST NOT be followed. This is a mitigation, not a control: the actual controls are structural (below).
  • Structural controls: the model has no network or shell tool; its only output is DSL source; that source is checked by the compiler, effect checker, scope typing and policy gate; scope is enforced again at the engine, tool-runner and proxy; budgets are enforced by the engine.

16.4 Recording and replay

Every model call is an effect. The engine stores the prompt and the response in object storage and records agent_call_recorded (model, token counts, hashes, latency). On replay the recorded response is returned without calling the model. Prompts are versioned (prompt_version in the record). Temperature is 0 by default for planner calls.

  • Logs: JSON, one line per event, fields ts, level, service, env, trace_id, span_id, request_id, tenant_id, run_id, effect_path, msg. No secrets, no tokens, no raw target payloads.
  • Traces: W3C traceparent propagated through REST, gRPC metadata and Pub/Sub attributes; one span per effect, tool call, scope check and DB transaction.
  • Metrics (examples): ff_runs_total{status}, ff_run_duration_seconds, ff_effects_total{kind,outcome}, ff_scope_decisions_total{decision,reason}, ff_limiter_denied_total{level}, ff_replay_nondeterminism_total, ff_agent_tokens_total, ff_agent_plan_rejected_total, ff_outbox_lag_seconds, ff_graph_ingest_seconds, ff_approvals_pending.
  • SLO candidates: scope check p99 under 100 ms; run submit-to-start p95 under 5 s; graph ingest p95 under 1 s per observation; outbox lag p99 under 10 s.

18.2 Security checklist

  • All inputs validated at the edge (schema) and again at the service (domain rules). Reject unknown fields.
  • Per-tenant isolation tests: for every list and get endpoint, a test with two tenants proves no cross-read.
  • Secrets only in Secret Manager; no secrets in env files, images, logs or events. Rotate signing keys (13.7).
  • Webhook destinations validated against SSRF (no private ranges, no redirects to them).
  • Dependencies pinned; images by digest; SBOM generated in CI; scanning blocks high severity findings.
  • Tool sandboxes: non-root, read-only filesystem, no capabilities, CPU and memory limits, wall-clock timeouts, no credentials.
  • Audit: every state-changing API call and every scope decision is logged with actor and request id; run events are immutable (10.4).
  • Abuse controls: signup and login throttles, per-tenant quotas (runs per day, tokens per month, storage), global kill switch.
  • Legal and policy: a program MUST have a scope document, and the product refuses to create runs against targets not covered by one. Users are responsible for operating only within programs they are authorized to test.

21. CSR graph snapshots and graph analytics

Postgres is the system of record for the graph (section 10.5). It is the wrong shape for whole-graph algorithms: PageRank or SCC over a join of entities and edges is pointer-chasing through B-trees. Analytics run on an immutable, in-memory Compressed Sparse Row (CSR) snapshot built from the system of record. The snapshot is a derived, disposable read model; it can always be rebuilt from Postgres.

21.1 Layout

One snapshot per (tenant_id, program_id). Nodes are renumbered to dense u32 indices 0..V-1; a side table maps index to entity id. A second, transposed CSR (incoming edges) is built alongside for reverse traversal and PageRank.

21.2 Building: counting sort in O(V + E)

build_csr(V, edges[(src, dst, label, conf)]):
  degree = [0; V]
  for e in edges: degree[e.src] += 1
  offsets = prefix_sum(degree) with a leading 0          // length V + 1
  cursor = copy of offsets[0..V]
  for e in edges:                                          // scatter
      i = cursor[e.src]; cursor[e.src] += 1
      targets[i] = e.dst; label[i] = e.label; conf[i] = e.conf
  for v in 0..V: sort row (targets, label, conf) by target // rows are short
  build transpose by running the same procedure with (dst, src)

Dense id assignment. Read entities ordered by entity_id, number them in that order, and keep the map. Because the order is deterministic, the same graph content yields the same snapshot bytes; the sha256 can therefore be compared across rebuilds.

21.4 Freshness: watermark, delta overlay, atomic swap

  • Every graph mutation appends a row to graph.change_events with a monotonically increasing seq (per tenant). A snapshot records the watermark_seq it reflects.
  • The graph service keeps a small in-memory delta overlay (added edges, removed edges, new nodes) for events with seq > watermark. Point queries (neighbours, BFS with small depth) consult snapshot plus overlay. Whole-graph analytics use the snapshot only and report the watermark in the response.
  • Compaction triggers when the overlay exceeds 1% of E or 5 minutes elapse with a non-empty overlay: rebuild in the background from Postgres at a consistent seq, write to gs://.../snapshots/{tenant}/{program}/{watermark}.ffcs, then swap an Arc pointer (ArcSwap in Rust, atomic.Pointer in Go). Readers holding the old snapshot keep it until they finish.
  • Stale or ageing entities (section 5.7) are excluded at build time using the configured stale_after; the exclusion rule is recorded in the header flags.
  • Cold start: load the newest snapshot from GCS (mmap after download), replay change_events after its watermark into the overlay.

22. Similarity search and DiskANN

Goal: answer "find assets like this one" and "find assets matching this free text" over millions of entities. 22.2 Metrics

  • L2: sum((a_i - b_i)^2) (skip the square root for ranking).
  • Cosine: normalise vectors at insert time, then use inner product. Distance = 1 - dot(a, b).
  • Inner product: distance = -dot(a, b).

The metric is fixed per index at creation. Distance kernels use SIMD (AVX2 or NEON) with a scalar fallback; the scalar version is the reference for tests.

  • Memtable: recent vectors in memory. Below roughly 50,000 vectors use exact brute force; above that, an in-memory Vamana graph. Flushed to a segment at a size or age threshold.
  • Segment: immutable DiskANN index file plus PQ codes. Written to local SSD, replicated to GCS for recovery.
  • Tombstones: a delete or an update adds the old vector to the tombstone set; queries over-fetch (k * 2 then filter) to compensate.
  • Merge: FreshDiskANN-style streaming merge. When tombstones exceed 20% of a segment, or the segment count exceeds 8, merge segments into a new one (insert new points with the Vamana insert, patch neighbours of deleted points, rebuild PQ if the codebook drifted). The old segments are deleted after the swap.
  • Isolation: one index per (tenant_id, program_id, model_id). Small tenants share nothing; this removes filtered search from the hot path and makes erasure a file deletion. Cross-program queries within a tenant fan out over indexes.

22.4 Vamana graph construction

Parameters: R = 64 (max out-degree), L_build = 100 (search list), alpha = 1.2, metric d

build(points P):
  G = random R-regular directed graph on P            // initial connectivity
  s = medoid(P)                                       // closest point to the centroid
  for pass in [alpha = 1.0, alpha = alpha_final]:     // two passes
    for p in random_permutation(P):
      (_, V) = greedy_search(G, s, query = p, L = L_build)    // V = visited set
      N_out(p) = robust_prune(p, V, alpha, R)
      for j in N_out(p):                              // add backward edges
        N_out(j) = N_out(j) + {p}
        if |N_out(j)| > R: N_out(j) = robust_prune(j, N_out(j), alpha, R)

greedy_search(G, start, query, L):
  list = {start}; visited = {}
  while list has unvisited points:
    p* = closest unvisited point in list to query
    visited += p*
    list = list + N_out(p*)
    keep only the L closest points in list
  return (top-k of list, visited)

robust_prune(p, V, alpha, R):                         // diversify neighbours
  V = V - {p}; N_out = {}
  while V not empty:
    p* = argmin over V of d(p, v)
    N_out += p*
    if |N_out| == R: break
    remove from V every v with alpha * d(p*, v) <= d(p, v)
  return N_out

Intuition: RobustPrune keeps an edge to p* and discards candidates that p* already "covers" (they are at least a factor alpha closer to p* than to p). With alpha above 1 some longer edges survive, which shortens search paths at the cost of degree.

22.5 On-disk layout and search

Segment file, sector size 4096 B. Node record = { vector f32[dim] | degree u32 | neighbours u32[R] }
  dim = 768, R = 64: 3072 + 4 + 256 = 3332 B, padded so a record never straddles a sector
  node i lives at sector (i / records_per_sector), slot (i mod records_per_sector)
  header sector: magic "FFDA", version, dim, metric, R, V, medoid, pq params, tombstone epoch

In RAM per segment: PQ codes, m bytes per vector (for example m = 96 of 8-bit sub-codes for dim 768),
                    the PQ codebooks, and a copy of the medoid and a small cache of hot nodes
On SSD per segment: full-precision vectors and the adjacency lists
beam_search(query, k, L, W):                    // W = beam width, 4 is a good start
  lut = pq_distance_table(query)                // m x 256 table, one per query
  list = {medoid}, visited = {}, results = {}
  while list has unvisited points:
    B = up to W closest unvisited points in list
    read the sectors of B from SSD concurrently        // one round trip of I/O per iteration
    for p in B:
      results[p] = exact_distance(query, full_vector(p))   // free: vector is in the same sector
      for n in neighbours(p) not in visited-or-list:
        list += (n, pq_distance(lut, code[n]))          // approximate, from RAM
    keep the L closest list entries by approximate distance
    visited += B
  return the k points in results with the smallest exact distance

Product quantisation. Split each vector into m sub-vectors, run k-means with 256 centroids on each sub-space (train on a sample of 100k points), store one byte per sub-vector. Distance to a code is the sum of m table lookups. The exact re-rank uses the full vector that arrives with the node sector, so quality depends mostly on graph quality and L.

First version. Implement the interface (22.9) with pgvector (HNSW index, vector_cosine_ops) in the graph database. It is correct, filterable with SQL and enough for hundreds of thousands of vectors. The segmented DiskANN engine is a drop-in replacement behind the same interface and is justified by a measured need (RAM cost, latency, million-scale tenants).

22.6 Hybrid search: text plus vector

Run lexical search (the trigram index from section 5.9, or Postgres full-text) and vector search independently, then fuse the ranked lists with reciprocal rank fusion:

score(d) = sum over lists L of  1 / (60 + rank_L(d))        // rank starts at 1; absent from a list contributes 0
Example: d is rank 1 in lexical and rank 3 in vector:  1/61 + 1/63 = 0.01639 + 0.01587 = 0.03226
         e is rank 2 in lexical only:                  1/62        = 0.01613
         so d outranks e.

RRF needs no score normalisation between the two systems, which have incomparable scales.

22.7 Filters

Because indexes are per program, tenant and program filtering is structural. Remaining filters (asset type, tag, last_seen range) are applied after retrieval with over-fetching (k * 4, retry with larger L when fewer than k survive). Highly selective filters (fewer than 1% of points match) fall back to an exact scan of the matching ids fetched from Postgres.

22.8 Near-duplicate detection without embeddings

  • SimHash (64-bit) over shingles of page text or banner tokens. Two documents are near duplicates when Hamming distance ≤ 3. Lookup uses multi-index hashing: split the 64 bits into 4 blocks of 16; any pair within distance 3 must match exactly on at least one block (pigeonhole), so query four hash tables and verify candidates with a popcount.
  • MinHash + LSH for set similarity (for example sets of linked hostnames or certificate SANs): 128 permutations, 32 bands of 4 rows; the probability two sets with Jaccard s collide in at least one band is 1 - (1 - s^4)^32.

Both are cheap, need no model, and are deterministic, so they can run inside the VM as pure builtins.

23. Distributed systems design

Flowforge is distributed from day one: several instances of each service, workers that crash, Pub/Sub that redelivers. This section states the model and the rules so that every component makes the same assumptions. It also lays out an optional path from "Postgres is the source of truth" to a self-built replicated log, for learning purposes.

23.1 Failure model and assumptions

  • Crash-stop with restart: processes may die at any instruction and later restart with durable state intact. Byzantine behaviour is out of scope.
  • Network: messages can be delayed, duplicated, dropped or reordered; partitions occur and heal. Timeouts are the only failure detector, so they are unreliable by nature.
  • Clocks: wall clocks skew and jump. Never use a wall clock to decide who owns something; use leases checked against a monotonic clock plus fencing tokens validated by the storage layer. Wall time is for display and for staleness heuristics only.
  • Delivery: Pub/Sub, Cloud Tasks and gRPC retries are at-least-once. Every handler is idempotent.
  • Principle: hashing and heartbeats are for efficiency (spread load, prefer a likely owner); leases with fencing are for safety (at most one effective writer). If hashing is wrong, work is merely duplicated or slow; if fencing is wrong, data is corrupt.

23.3 Work distribution

  • Membership: workers write a heartbeat row (or Redis key with TTL) every 5 seconds; a worker is considered live for 15 seconds after its last heartbeat. A gossip protocol (SWIM-style, with suspicion) is the stretch goal.
  • Rendezvous (highest-random-weight) hashing: for a key k and live workers w, the owner is argmax over w of hash(k, w). It needs no ring state and moves only the keys of a failed worker. Used for: run affinity (keep a run's VM snapshot hot), target affinity (a host's requests go through the same tool-runner, which makes per-target rate limits local and accurate).
  • Consistent hashing with virtual nodes is the alternative when the key space needs weighting; keep both implementations behind a Placement trait and test them for balance and minimal movement.
  • Claiming: the preferred owner tries to acquire the lease first; other workers delay their attempts by their rank in the hash order. If the preferred owner is dead, the next in line takes over after the lease expires. Ranks only change who tries first, never who may write.
  • Back-pressure: worker concurrency is bounded by a semaphore per tenant and per tool class; the queue is the buffer; a full queue returns RESOURCE_EXHAUSTED with retry_after.

23.4 The EventStore abstraction

The engine depends on a narrow trait, so the implementation can change from Postgres to a replicated log without touching the VM or the engine logic.

// Specification-level signature (Rust shown; port the semantics to any language)
pub struct Fence(pub u64, pub u64);            // (term, counter); compared lexicographically

pub trait EventStore: Send + Sync {
    /// Append events if the stream head equals `expected_seq` AND `fence` is the current fence.
    /// Atomic. Returns the new head. Errors: SeqConflict, Fenced.
    async fn append(&self, run: RunId, expected_seq: u64, fence: Fence, events: &[Event])
        -> Result<u64, AppendError>;

    async fn read(&self, run: RunId, from_seq: u64, limit: usize) -> Result<Vec<Event>, StoreError>;
    async fn subscribe(&self, run: RunId, from_seq: u64) -> Result<EventStream, StoreError>;

    async fn save_snapshot(&self, run: RunId, at_seq: u64, bytes: Bytes) -> Result<(), StoreError>;
    async fn load_snapshot(&self, run: RunId) -> Result<Option<(u64, Bytes)>, StoreError>;

    /// Lease: returns a fence strictly greater than any previous fence for this run.
    async fn acquire_lease(&self, run: RunId, owner: WorkerId, ttl: Duration) -> Result<Lease, LeaseError>;
    async fn renew_lease(&self, lease: &Lease, ttl: Duration) -> Result<Lease, LeaseError>;
    async fn release_lease(&self, lease: Lease) -> Result<(), StoreError>;

    /// Runs that are ready for work: unleased or lease expired, with a due timer or pending event.
    async fn list_ready(&self, shard: Shard, limit: usize) -> Result<Vec<RunId>, StoreError>;
}

Properties every implementation must satisfy (these become the conformance suite in 23.8): (1) after a successful append at head h the next append must name expected_seq = h + n; (2) an append carrying an older fence fails even if expected_seq matches; (3) a read after a successful append observes it (read-your-writes) and reads are never reordered; (4) acquire_lease returns strictly increasing fences, including across restarts of the store.

Implementation A: Postgres (default)

The schema in section 10.4. append is a single transaction: SELECT ... FOR UPDATE on the run row, check head_seq = expected_seq AND fence = $fence, insert events, update head_seq. Lease acquisition does UPDATE runs SET fence = fence + 1, lease_owner = $w, lease_expires = now() + $ttl WHERE run_id = $r AND (lease_expires < now() OR lease_owner = $w) RETURNING fence. The now() here is the database clock, which is the single time source for lease expiry, so worker clock skew cannot break it. list_ready uses FOR UPDATE SKIP LOCKED.

Implementation B: sharded Raft log (optional, learning track)

  • Sharding: shard = hash(run_id) mod S (S fixed at deployment, for example 64; resharding is done by splitting a shard's key range, not by changing S). Each shard is a Raft group of 3 or 5 replicas; the replicas of many shards share processes (multi-Raft) and share a transport.
  • State machine: apply committed commands Append{run, expected_seq, fence, events}, AcquireLease, RenewLease, SaveSnapshot. The state machine is deterministic and checks expected_seq and fence at apply time, so a stale command from a deposed leader is rejected when it commits.
  • Fence: (raft term, per-term counter). A new lease acquisition after a leader change always yields a larger term, which preserves strict monotonicity without a clock.
  • Reads: ReadIndex (leader confirms leadership with a heartbeat round, waits for the applied index to reach the commit index at request time) for linearizable reads; follower reads allowed for subscribe with a lag bound.
  • Log and snapshots: segmented write-ahead log with CRC per record and fsync policy (group commit); snapshot of the state machine every N applied entries, then truncate; install-snapshot RPC for slow followers.
  • Membership change: single-server changes (one at a time) first; joint consensus as a stretch goal.
  • Raft invariants to test: election safety (at most one leader per term), leader append-only, log matching, leader completeness, state machine safety.
  • Deployment: replicas are stateful with persistent disks, so they need GKE StatefulSets (not Cloud Run). This is the main infrastructure reason Implementation B is optional.

23.6 Distributed queries and analytics

  • Search and similarity: scatter-gather. The coordinator sends the query to every shard or segment, each returns its local top-k with distances, the coordinator merges with a k-way merge (heap), applies tombstones and filters, and returns. Hedged requests (send a duplicate to a second replica after the p95 latency) cut tail latency; deadlines propagate in gRPC metadata.
  • Graph analytics at scale (stretch): partition the CSR by node range, run Pregel / bulk-synchronous-parallel supersteps (each worker processes its vertices, sends messages to neighbours, barrier, repeat). PageRank, connected components (label propagation) and BFS map directly onto it. Start single-process with a thread-per-partition runner and message queues, then move to processes. One snapshot per program fits in one machine for the foreseeable future, so this is for learning, not need.

23.7 Messaging and cross-service consistency

  • Outbox: a service writes its state change and an outbox row in one transaction; a relay publishes to Pub/Sub and marks the row. A crash between publish and mark causes a duplicate, never a loss.
  • Inbox: consumers record the event id in an inbox table inside the transaction that applies the effect; a duplicate hits the unique constraint and is acknowledged without effect.
  • Ordering: Pub/Sub ordering keys per run or per entity where order matters; consumers still tolerate gaps by checking seq.
  • No distributed transactions: cross-service workflows are sagas with compensation (section 9.6). Two-phase commit is explicitly not used.
  • Dead letters: after N failed deliveries a message goes to a dead-letter topic with the failure reason; an operator tool replays or discards it.
  • Distributed tracing: W3C traceparent in gRPC metadata and in Pub/Sub attributes, so one trace spans gateway, engine, tool-runner, graph and notifier.

24. Modular architecture and module contracts

The system is built as a set of modules that can be implemented, tested and benchmarked one at a time, in isolation, in any order that respects the dependency rules. The style is clean (hexagonal, ports and adapters): a pure core with no I/O, surrounded by traits (ports) whose real implementations (adapters) live at the edge. A module is "done" only when it satisfies the definition in 24.6, which includes its tests and benchmarks.

24.1 Principles

  • Pure core, effects at the edge. Domain logic (scope decision, DSL, VM, merge, limiters, CSR algorithms, distance kernels) takes values and returns values. It does not read the clock, generate randomness, touch the network or the disk, or log to a global.
  • Ports only at real boundaries. A trait exists where a second implementation or a fake is needed (24.4). Do not wrap every struct in a trait.
  • Every module ships with an in-memory fake of each port it exposes, so its consumers can be tested without Postgres, Redis or the network.
  • Dependencies point inward and downward (24.3). No cycles. Enforced by a test that parses the package metadata (25.2, test arch/deps).
  • Determinism. Given the same inputs and the same seed, a module produces the same outputs. Time and randomness come from ports.
  • Services are thin. A service binary wires adapters to modules (gRPC handlers, config, telemetry). It contains no domain logic and has few tests of its own beyond wiring.

24.5 Isolation rules for implementers

  • A module's tests MUST pass with only its own dependencies built (cargo test -p ff-scope never compiles Postgres drivers or tonic).
  • Conformance data is read from conformance/<suite>/; a module never embeds expected values that also exist as data.
  • No module reads environment variables, the system clock, or global state. Configuration arrives as a struct.
  • Public API changes in a lower layer require updating the module's CHANGELOG entry and its conformance data version.
  • Error types are per module (thiserror in Rust, sentinel errors in Go) and mapped to gRPC and REST codes only in services (section 11.8).

24.6 Definition of done for a module

An agent or a human may mark a module complete only when all of the following are true. cargo xtask verify-module <name> checks the mechanical items and fails otherwise.

  1. The public surface in 24.3 exists, is documented (/// on every public item), and has no unwrap() or expect() outside tests (Clippy lint unwrap_used denied).
  2. All required test cases for the module in 25.3 exist as tests whose names start with the case ids (for example scope_001_trailing_dot), and pass.
  3. All conformance suites listed for the module in modules.toml exist under conformance/ and pass.
  4. All property tests in 25.4 for the module exist and pass with 1,000 cases locally and 100,000 in the nightly job.
  5. Fuzz targets in 25.5 exist and run for 60 seconds without findings (nightly: 30 minutes).
  6. The benchmarks in 25.8 for the module exist, run with cargo bench -p <name>, and a baseline result file is committed under bench/results/<module>/.
  7. No forbidden dependency edge (arch/deps test passes); cargo clippy -- -D warnings and cargo fmt --check are clean.
  8. Any unsafe block is covered by a Miri test and carries a // SAFETY: comment stating the invariant.
  9. A short README.md in the module: purpose, the section of this spec it implements, how to run its tests and benchmarks, and known limitations.

25.2 Rules for all tests

  • Deterministic. No wall-clock sleeps (use FakeClock), no real network in unit tests, no shared mutable global. A randomised test prints its seed on failure and accepts the seed through an environment variable (FF_SEED) to reproduce.

  • Architecture test arch/deps.   • Every bug gets a regression test named regress_<issue>, ideally a conformance case.
  • Coverage is a signal, not a target: report line and branch coverage (cargo llvm-cov); pure modules are expected to stay high, and a drop below the previous baseline needs an explanation in the PR. For ff-scope and ff-limiter also run mutation testing (cargo-mutants) nightly; surviving mutants in decision logic are treated as missing tests.
  • No flaky tests. A test that fails intermittently is quarantined within a day and fixed or deleted within a week.

25.6 Differential tests

  • Tree-walking evaluator versus bytecode VM (every vm/run case plus generated programs).
  • Naive reference versus optimised implementation: CSR algorithms versus adjacency-list versions; GCRA/atomic version versus the timestamp-list model; SIMD versus scalar kernels; rendezvous versus a slow recomputation.
  • Exact versus approximate: BruteForceIndex versus DiskANN and versus pgvector (recall, not equality).
  • Implementation versus implementation: MemStore versus Postgres versus Raft behind the EventStore conformance suite.
  • Language versus language: Go reference and Rust port run the same conformance/ data and must produce identical outputs (section 20.2).

25.7 Simulation and invariants

ff-sim runs the engine, several workers, the event store, a fake tool executor, a fake scope service and a fake Pub/Sub inside one process, with every call going through an adapter that can drop, delay, duplicate, reorder or fail it, and with a simulated clock. A scenario is (seed, fault_profile, workload). After the run, check_invariants(history) must return no violations:

IdInvariant
inv_01Per run, event seq is contiguous from 1 with no duplicates.
inv_02Each fence value has at most one writer, and fences strictly increase over time.
inv_03No event is committed by a writer whose fence was already superseded.
inv_04Every tool effect has at most one recorded result; the tool executor may have run it more than once only with the same idempotency key.
inv_05Replaying a run's log reproduces its terminal state and its effect order.
inv_06No active tool call was issued for a target without a prior allow decision in the same run for that target and scope version.
inv_07Every saga that failed has either completed compensation in reverse order or is marked as needing operator action.
inv_08Every alert-worthy event produced exactly one delivered alert per rule and dedupe window (duplicates in the transport do not produce duplicate alerts).
inv_09The graph state after the simulation equals the state obtained by applying the set of recorded observations once each in a canonical order.
inv_10Per-target request rate observed by the fake tool executor never exceeds the configured ceiling over any window.
inv_11Every submitted run reaches a terminal state, or is still non-terminal only because the workload ended (liveness within a bounded number of simulated seconds after faults stop).

Fault profiles: none, crashy (workers killed at random instants), lossy (drop and duplicate messages), slow (random latency spikes), partitioned (workers cut from the store for intervals), skewed (clock offsets), and a chaos mix. CI runs 200 seeds per profile per PR and 10,000 nightly; a failing seed is printed and added to conformance/sim/regress_seeds.json.

25.8 Benchmarks

Methodology (applies to all).

  • Micro benchmarks use criterion (statistical, with warm-up and outlier reporting); where CI noise is a problem also record instruction counts (iai-callgrind or perf stat) because they are stable across machines.
  • Macro benchmarks live in bench/ and use a purpose-built load generator (open-loop with a target rate, to avoid coordinated omission). They report throughput and latency percentiles p50, p90, p99, p99.9 from an HDR histogram.
  • Fixed seeds and generated datasets (xtask gen-bench-data) so any two runs use identical inputs. External datasets (SIFT1M, GIST1M) are downloaded by script, never committed.
  • Record the environment in every result: CPU model, cores, RAM, OS, kernel, rustc version, build profile (--release with lto = "thin", codegen-units = 1), commit, and whether the CPU governor was pinned.
  • Results format: one JSON file per run under bench/results/<module>/<date>-<commit>.json with {bench_id, params, metrics: {name: value, unit}, env}; xtask bench-compare <baseline> <new> prints deltas.
  • Targets are measured, then fixed. The first run of each benchmark produces the baseline. Acceptance thresholds below are expressed as shapes and ratios (scaling, speed-ups, recall floors) that can be checked without guessing absolute numbers; absolute budgets are set after the baseline and recorded in bench/budgets.toml.
  • Regression gate: nightly compares against the stored baseline; a regression of more than 10% in a stable metric (instruction counts) or 20% in a timing metric, sustained over three runs, opens an issue. A PR that deliberately slows something updates the baseline with a stated reason.
  • Every benchmark also tracks allocations per operation (dhat or a counting allocator) because accidental allocation in hot paths is the most common regression.

25.11 CI stages

  1. Fast (every push): fmt, clippy -D warnings, cargo deny (licences, advisories), arch/deps, unit and conformance tests, property tests at 1,000 cases, loom tests, snapshot tests.
  2. Integration (every PR): Postgres, Redis and the Pub/Sub emulator through testcontainers; adapter and service tests; EventStore suite against Postgres; 200 simulation seeds; 60-second fuzz smoke.
  3. Nightly: property tests at 100,000 cases, 30-minute fuzz per target, Miri on unsafe modules, sanitizers (address, thread), mutation testing on ff-scope and ff-limiter, 10,000 simulation seeds across all fault profiles, full benchmark suite with comparison to the baseline, coverage report.
  4. Post-deploy to dev: end-to-end script, the system benchmarks b_sys_*, and a chaos run that kills workers and forces a Postgres failover, followed by the invariant checker over the exported logs.

25.12 Guidance for a coding agent

  • Work on one module at a time in the order of 24.7. Start by reading the module's section, its row in 24.3, its test table in 25.3 and its modules.toml entry.
  • Write the test list and the conformance data first (they will fail), then implement until they pass. Do not edit expected values to make a test pass without a written justification that cites this specification.
  • When this specification is ambiguous or inconsistent (for example fields flagged verify), do not guess silently: add a docs/open-questions.md entry in the module, pick the most conservative behaviour (fail closed for anything touching scope), and add a test that pins the choice.
  • Finish by running cargo xtask verify-module <name> and cargo xtask bench-module <name>, commit the baseline result, and summarise: what was implemented, what the benchmark showed, what remains.
  • Never weaken a safety invariant (scope, fencing, idempotency, determinism) to improve a benchmark.
